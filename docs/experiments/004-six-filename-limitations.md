# 실험 004: 파일명 생성의 여섯 가지 잔여 한계 통합 보완

작성일: 2026-08-08
대상 프로젝트: Local File AI

## 실험 목적

실험 001 보고서에 남은 다음 여섯 가지 한계를 하나의 통합 실험에서 보완한다.

1. 첫 페이지 또는 앞부분 2,000자만 사용해 뒤쪽 핵심 정보를 놓치는 문제
2. subject, topic, semester의 의미 정확성을 LLM 출력에만 의존하는 문제
3. 동일 최종 파일명이 존재할 때 적용을 건너뛰는 문제
4. subject와 topic의 사실성을 별도로 검증하지 않는 문제
5. 한글·영문 표기 통일과 사용자별 명명 관례를 지원하지 않는 문제
6. `extension_fixed`가 구조화 조립까지 포함해 의미가 부정확한 문제

이번 실험의 목표는 LLM을 완전히 제거하는 것이 아니라, LLM의 후보 제안을 문서
근거·사용자 예시·결정론적 백엔드 규칙으로 검증하는 것이다.

## 지난 코드의 한계

### 1. 제한된 문서 입력

`MAX_FIRST_PAGE_CHARS = 2000`이 추천 입력의 상한이었고 PDF 추출기는 첫 페이지만
읽었다. 제목, 과목, 학기, 결론이 2페이지 이후에 있는 문서는 해당 정보를 LLM과
분류기가 볼 수 없었다.

### 2. LLM 의미 출력의 무검증 사용

구조화 응답으로 subject, topic, semester를 분리했지만 각 값이 실제 문서에 있는지
검사하지 않았다. LLM이 유사 예시의 주제를 복사하거나 존재하지 않는 학기를
추측해도 안전한 문자열이라는 이유만으로 파일명에 들어갔다.

### 3. 동일 파일명 충돌

실험 001 시점에는 대상 파일명이 이미 존재하면 `skipped`로 처리했다. 이 문제는
실험 002에서 번호 접미사로, 실험 003에서 150자 제한과 원자적 무덮어쓰기 이동으로
단계적으로 개선됐다. 이번 통합 실험은 해당 변경이 현재 전체 코드에서도 유지되는지
회귀 테스트로 함께 검증한다.

### 4. subject/topic 사실성 부재

document_type은 임베딩 분류기의 category로 교정했지만 subject와 topic은 LLM 값을
그대로 사용했다. 따라서 category는 맞아도 과목이나 주제가 다른 파일명이 만들어질
수 있었다.

### 5. 표기 관례 미지원

`인공지능`과 `AI`, `데이터베이스`와 `DB`, `운영체제`와 `OS`처럼 같은 의미의
표기가 섞여도 항상 동일한 규칙으로 정리되지 않았다. 이미 승인된 유사 파일의
표기를 새 파일명에 반영하는 경로도 없었다.

### 6. 모호한 상태 이름

`SuggestResult.extension_fixed`는 처음에는 누락된 확장자를 붙였는지를 뜻했다.
구조화된 구성요소를 조립한 뒤에도 True가 되면서 실제 의미가 “파일명 후처리가
일어남”으로 넓어졌지만 필드 이름은 그대로였다.

## 변경 코드를 통한 보완점

### 1. 최대 5페이지 및 6,000자 균형 표본

`MAX_ANALYSIS_CHARS = 6000`을 새로 도입하고 `/organize`가 추천 분석 시 이 값을
사용하도록 변경했다.

PDF 추출기는 첫 페이지만 읽는 대신 앞쪽 최대 5페이지를 읽는다. 추출된 문서가
6,000자를 넘으면 `select_analysis_text()`가 다음 비율로 표본을 구성한다.

```text
앞부분 50% + 중간 25% + 뒷부분 25%
```

구간 사이에는 `[중간 생략]` 표시를 넣어 연결되지 않은 문장이 하나로 오해되는 것을
줄였다. DOCX, PPTX, HWPX 등 전체 텍스트가 추출되는 형식에도 같은 앞·중간·뒤
선택을 적용했다.

### 2. semester의 문서 근거 우선

LLM이 출력한 semester를 직접 사용하지 않고 문서 표본에서 다음과 같은 패턴을
직접 찾아 표준 형식으로 변환한다.

```text
2026년 1학기 → 2026-1
2026-1       → 2026-1
```

본문에서 학기를 찾지 못하면 LLM이 값을 출력했더라도 파일명에서 제외한다.

### 3. 동일 이름 자동 번호 및 원자적 적용 유지

실험 002·003의 보완을 통합 상태로 유지했다.

```text
이름.pdf
이름 (1).pdf
이름 (2).pdf
```

접미사를 포함해 150자를 넘지 않도록 stem을 줄이며, `os.link()` 기반 원자적
무덮어쓰기 이동으로 외부 경쟁자가 먼저 이름을 차지하면 다음 번호를 선택한다.

### 4. subject/topic 본문 근거 검증

subject와 topic을 파일명에 넣기 전에 다음 과정을 적용한다.

1. 금지 문자와 공백을 정규화한다.
2. `_` 기준으로 의미 토큰을 분리한다.
3. `과제`, `보고서`, `자료`, `최종` 같은 일반 문서유형 단어를 근거 판정에서
   제외한다.
4. 남은 핵심 토큰이 모두 문서 표본에 존재할 때만 구성요소를 유지한다.

예를 들어 LLM이 `머신러닝 과제`를 topic으로 출력했는데 본문에는 `과제`만 있고
`머신러닝`이 없으면 topic 전체를 제거한다. 일반어 하나가 일치했다는 이유로 환각
주제가 통과하지 않는다.

### 5. 승인·유사 예시 기반 표기 관례

RAG로 전달된 승인·유사 파일명의 토큰을 확인해 같은 의미 그룹의 표기를 현재
파일명에 적용한다.

현재 지원 그룹:

```text
인공지능 ↔ AI
운영체제 ↔ OS
데이터베이스 ↔ DB
컴퓨터네트워크 ↔ 네트워크 ↔ NETWORK
```

현재 문서 subject가 `인공지능`이고 유사 승인 파일이 `AI_머신러닝_과제.pdf`라면
사실 정보는 현재 본문에서 확인하되 최종 표기만 `AI`로 맞춘다. 예시의 주제를
현재 문서 사실로 복사하지 않도록 프롬프트에도 명시했다.

### 6. `filename_normalized`로 상태명 정리

`SuggestResult`의 실제 저장 필드를 `filename_normalized`로 변경했다. 이 값은
확장자 교체, 구조화 요소 조립, 안전한 파일명 정규화 등 최종 파일명 후처리가
발생했음을 뜻한다.

기존 호출자가 즉시 깨지지 않도록 `extension_fixed`는 읽기 전용 호환 property로
남겼으며 내부 새 코드는 `filename_normalized`를 사용한다.

```text
인공지능 트랜스포머 과제 2026년 1학기 제출
```

이를 통해 첫 페이지만 읽는 기존 코드라면 얻을 수 없는 정보가 실제 모델 입력과
최종 파일명에 반영되는지 확인했다.

## 실제 결과

### 첫 실제 실행과 발견된 문제

5페이지 내용은 정상 추출됐지만 LLM은 유사 예시의 주제를 복사했다.

```json
{
  "subject": "인공지능",
  "topic": "머신러닝 과제",
  "document_type": "과제",
  "semester": "2026-1"
}
```

당시 검증은 topic 토큰 중 하나만 본문에 있어도 통과시켰다. 본문에 일반어 `과제`가
있어 근거 없는 `머신러닝`까지 통과했고 결과는 다음과 같았다.

```text
AI_머신러닝_과제_과제_2026-1.pdf
```

이 실패를 바탕으로 일반 문서유형 단어를 근거 판정에서 제외하고 핵심 토큰 전부가
본문에 있어야 통과하도록 강화했다.

### 최종 실제 LLM 원시 응답

강화 후 동일 PDF를 다시 실행했을 때 모델은 여전히 다음 값을 출력했다.

```json
{
  "subject": "인공지능",
  "topic": "머신러닝 과제",
  "document_type": "과제",
  "semester": "2026-1"
}
```

모델 자체의 환각은 남았지만 백엔드 검증이 본문에 없는 `머신러닝`을 탐지해 topic을
제거했다.

### 최종 결과

```json
{
  "category": "assignment",
  "recommended_folder": "assignment",
  "recommended_filename": "AI_과제_2026-1.pdf",
  "confidence": 0.88,
  "reason": "사용자 승인 예시 기반 분류 (신뢰도 88%), 파일명은 exaone3.5:2.4b 생성 (slim 모드)"
}
```

확인 결과:

- 5페이지의 `인공지능`과 `2026년 1학기`가 추출됐다.
- 사용자 예시의 표기 관례에 따라 `인공지능`이 `AI`로 표현됐다.
- 예시에서 잘못 복사한 `머신러닝`은 최종 파일명에서 제거됐다.
- 본문 학기는 `2026-1`로 표준화됐다.
- LLM 재시도는 없었다.
- 실제 생성 시간은 2.94초였다.
- `filename_normalized`는 True였다.

실제 문서의 참 주제인 `트랜스포머`는 LLM이 구조화 응답에 넣지 않아 최종 파일명에
포함되지 않았다. 이 결과는 사실 검증이 환각을 막을 수는 있지만 누락된 정보를
새로 만들어내지는 못한다는 한계를 보여준다.

## 테스트 과정에서 발생한 실패

### 존재하지 않는 테스트 파일 지정

처음 집중 테스트 명령에서 `backend/tests/test_extraction.py`를 지정했지만 해당 파일이
없어 테스트가 실행되지 않았다. 이후 실제 파일명인 새
`test_extraction_analysis.py`를 만들고 명령을 수정했다.

### 기존 환각 허용 테스트 실패

새 사실 검증 도입 후 기존 테스트 하나가 본문에 없는 `운영체제/스케줄링/2026-1`이
제거되면서 실패했다. 테스트 본문과 기대값을 실제 근거가 일치하도록 수정했다.

### 프롬프트 문구 호환 테스트 실패

전체 테스트 첫 실행은 다음 결과였다.

```text
1 failed, 186 passed
```

RAG 안내 문구를 바꾸면서 기존 테스트가 확인하던 `비슷한 문서들은` 표현이 사라진
것이 원인이었다. 새 안전 지시를 유지하면서 기존 표현도 포함하도록 수정했다.

## 보완 코드의 한계

### 1. 전체 문서를 읽는 것은 아님

PDF는 최대 5페이지만 읽는다. 6페이지 이후에만 핵심 정보가 있으면 여전히 놓친다.
6,000자를 넘는 문서는 앞·중간·뒤 표본만 사용하므로 표본 사이 정보도 누락될 수
있다. 입력 증가로 임베딩 및 LLM 처리 시간과 메모리 사용량도 늘어난다.

### 2. 사실 검증은 문자열 포함 기반

현재 subject/topic 검증은 정규화된 핵심 토큰이 본문에 문자 그대로 있는지를 본다.
동의어, 약어, 조사 변화, 번역 표현을 충분히 이해하지 못한다. 사실인 `인공지능`과
`AI`가 서로 다른 문자열이라 문서와 LLM 출력 조합에 따라 제거될 수 있다.

### 3. 환각 제거가 정보 복구를 보장하지 않음

실제 실험에서 LLM의 `머신러닝` 환각은 제거했지만 참 주제 `트랜스포머`를 자동으로
복원하지 못했다. 보수적인 검증은 틀린 이름을 줄이는 대신 구체성이 낮은
`AI_과제_2026-1.pdf`를 만들 수 있다.

### 4. 사용자 관례는 제한된 사전 기반

현재 표기 그룹은 AI, OS, DB, NETWORK 계열 네 종류뿐이다. 임의의 과목 약칭이나
사용자 고유 규칙을 일반적으로 학습하지 않는다. 또한 전달된 RAG 예시가 반드시
사용자가 직접 승인한 예시인지 데이터셋 예시인지 엄격히 구분하지 않는다.

### 5. 충돌 처리의 파일 시스템 제약

동일 이름 자동 번호는 구현됐지만 원자적 이동이 hard link에 의존한다. 다른 볼륨,
일부 네트워크 공유, hard link 미지원 파일 시스템에서는 `atomic_move_error`로
실패한다. 전체 경로 길이도 아직 별도로 제한하지 않는다.

### 6. `extension_fixed`는 완전히 제거되지 않음

내부 저장 필드는 `filename_normalized`로 바로잡았지만 하위 호환을 위해
`extension_fixed` property를 남겼다. 구버전 호출자가 사라진 뒤 별도 제거 작업이
필요하다.

### 7. category 정확도에 계속 의존

document_type은 LLM보다 정확한 임베딩 분류기로 교정하지만 분류기 역시 완벽하지
않다. 잘못된 category가 결정되면 파일명의 문서 유형도 일관되게 잘못 교정된다.

## 결론

여섯 한계를 모두 코드 또는 통합 검증 범위에서 다뤘다. 입력 범위를 5페이지와
6,000자로 확대했고, subject/topic/semester를 문서 근거로 검증하며, 사용자 예시의
표기 관례를 제한적으로 반영했다. 동일 이름은 안전한 번호로 처리되고 상태명은
`filename_normalized`로 명확해졌다.

다만 “보완”은 “완전 해결”을 의미하지 않는다. 실제 LLM 실험은 모델이 유사 예시의
주제를 복사할 수 있음을 다시 보여줬다. 백엔드는 그 환각을 제거했지만 참 주제를
복구하지 못했다. 다음 실험은 문자열 포함 검증을 임베딩 기반 근거 문장 검증으로
확장하고, topic이 제거됐을 때 본문 핵심어 후보를 다시 추출하는 복구 경로를 다루는
것이 적절하다.
