# 실험 005: slim 파일명 생성 지연 단축

작성일: 2026-08-08
대상 프로젝트: Local File AI

## 실험 목적

실험 004의 실제 5페이지 PDF 조건에서 문서 추출부터 최종 파일명 출력까지
5.8929초가 걸렸고, 그중 LLM 생성이 5.7257초였다. 전체 시간의 약 97%를 차지하는
slim 생성 구간을 줄이되 JSON 계약 성공률과 파일명 안전 검증을 유지하는 것이
목적이다.

## 지난 코드의 한계

slim 모드는 분류기에서 category와 document_type을 이미 알고 있지만 LLM에
document_type을 다시 생성하도록 요청했다. 현재 경로와 상세 파일명 규칙도
프롬프트에 포함했지만 slim의 세 가지 의미 요소 추출에는 필요하지 않았다.

또한 Ollama의 `num_predict` 상한을 설정하지 않아 모델이 필요한 JSON 이후에도
불필요한 토큰을 생성할 여지가 있었다.

기준 측정값은 다음과 같다.

```text
5페이지 PDF 추출:       0.1655초
LLM 생성:               5.7257초
검증·파일명 조립:       0.0017초
전체:                   5.8929초
```

## 변경 코드를 통한 보완점

### slim 출력 필드 축소

기존 네 필드에서 백엔드가 이미 알고 있는 document_type을 제거했다.

```json
{
  "subject": "",
  "topic": "",
  "semester": ""
}
```

document_type은 기존대로 임베딩 분류기의 category에서 결정한다.

### slim 전용 최소 사용자 프롬프트

full과 공유하던 사용자 프롬프트 대신 `build_slim_user_prompt()`를 추가했다.
다음 정보만 전달한다.

- 현재 파일명과 확장자
- 문서 분석 표본
- 표기 관례로 참고할 유사 파일명
- 예시 주제를 복사하지 말라는 짧은 지시

현재 경로, category 설명, 폴더 생성 규칙, confidence와 reason 설명은 제외했다.

### 출력 토큰 상한

`LOCAL_FILE_AI_SLIM_NUM_PREDICT` 설정을 추가했으며 기본값은 64다. `/organize`가
slim 모드일 때만 Ollama options의 `num_predict=64`를 전달한다. full 모드는 기존
출력 길이를 유지한다.

### 클라이언트 확장

`llm.client.generate()`에 선택적 `num_predict` 인자를 추가했다. 값이 없으면 기존
동작과 동일하고, slim 경로에서만 options에 포함된다.

## 첫 최적화 시도 실패

처음에는 시스템 프롬프트를 지나치게 짧게 줄였다. 실행 시간 중앙값은 3.112초로
줄었지만 세 번 모두 다음과 같은 계약 밖 응답을 생성했다.

```json
{"filename": "최종"}
```

각 요청은 검증 실패 후 재시도했지만 최종적으로 `llm_invalid_json`이 됐다. 속도만
빠르고 성공률이 0%이므로 이 프롬프트는 채택하지 않았다.

실패를 바탕으로 다음을 명시했다.

- 허용되는 JSON 키 세 개
- 각 키의 의미
- 본문에 없으면 빈 문자열
- filename, document_type, 확장자, 설명 출력 금지

## 실험 환경과 방법

- 실제 모델: `exaone3.5:2.4b`
- 문서: 실험 004와 같은 5페이지 PDF
- 핵심 내용: 5페이지의 `인공지능 트랜스포머 과제 2026년 1학기 제출`
- 사용자 표기 예시: `AI_머신러닝_과제_2025-2.pdf`
- 반복 횟수: 3회
- 생성 상한: 64토큰
- 측정 범위: PDF 추출 → LLM → 의미 검증 → 최종 파일명 조립

## 실제 결과

### 실행 1

```text
추출: 0.083초

전체: 2.557초
재시도: 없음
```

### 실행 2

```text

재시도: 없음
```

### 실행 3

```text
추출: 0.005초
LLM:  0.365초
전체: 0.370초
재시도: 없음
```

중앙값:

```text
전체 0.390초
```

세 번 모두 정상 JSON을 반환하고 Pydantic 및 의미 검증을 통과했다. 최종 파일명은
동일하게 다음과 같았다.

```text
인공지능_트랜스포머_과제_2026-1.pdf
```

### 기준 대비

기준 단일 측정 5.8929초와 최적화 후 첫 실행 2.557초를 비교하면 약 56.6% 감소했다.
최적화 후 3회 중앙값 0.390초는 기준보다 약 93.4% 작다.

다만 기준은 단일 실행이고 최적화 값은 반복 실행을 포함하므로 중앙값 비교는 모델
캐시와 시스템 상태의 영향을 받는다. 가장 보수적인 비교는 첫 실행 기준 5.89초에서
2.56초로 줄었다는 결과다.

## 테스트 과정에서 발생한 실패

전체 테스트 첫 실행에서는 다음 결과가 나왔다.

```text
1 failed, 187 passed
```

테스트가 `document_type`이라는 문자열이 프롬프트 어디에도 없어야 한다고 검사했지만,
새 프롬프트의 “document_type을 출력하지 마십시오”라는 금지 문장에 해당 문자열이
있었다. JSON 출력 키로 요구되지 않는지를 검사하도록 테스트를 수정했다.

최종 전체 테스트:

```text
188 passed, 2 warnings
```

`git diff --check`도 통과했다.

## 보완 코드의 한계

1. 64토큰은 현재 세 필드 JSON에는 충분했지만 매우 긴 subject/topic이나 모델별
   토큰화 차이로 JSON이 잘릴 수 있다. 이 경우 기존 1회 재시도가 발생해 오히려
   지연이 커진다.

2. 측정값은 모델 메모리 캐시와 Ollama 상태에 크게 영향받는다. 프로세스 재시작 후
   모델을 처음 적재하는 cold start는 여전히 수십 초가 걸릴 수 있다.

3. 이번 최적화는 slim 모드만 대상으로 한다. 7.8B full 모드의 폴더·근거 생성
   시간은 줄이지 않았다.

4. 측정에는 실제 `/organize`의 임베딩 계산과 ChromaDB RAG 조회 시간이 포함되지
   않았다. 전체 사용자 체감 시간에는 이 비용이 추가된다.

5. 짧은 프롬프트는 모델별 지시 준수율이 달라질 수 있다. 실제 exaone3.5:2.4b에서
   3회 성공했지만 더 다양한 문서에 대한 품질·성공률 평가가 필요하다.

6. 모델은 `인공지능 트랜스포머`를 subject 하나로 묶었다. 최종 파일명은 사실에
   부합하지만 subject/topic 경계의 의미 품질이 항상 개선된 것은 아니다.

## 결론

LLM 생성이 전체 지연의 병목임을 확인하고 slim 출력 계약과 프롬프트를 최소화했다.
지나친 축약으로 성공률 0%가 된 첫 시도는 폐기했고, 키를 명확히 제한한 두 번째
프롬프트는 실제 모델 3회 모두 성공했다.

동일 조건의 첫 실행은 5.89초에서 2.56초로 약 56.6% 감소했고, 워밍업 후에는
0.37~0.39초에 최종 파일명을 출력했다. 다음 실험은 실제 `/organize` 전체 경로를
계측해 임베딩·RAG 시간을 분리하고, cold start를 줄이는 선제 모델 워밍업을 다루는
것이 적절하다.
