# 실험 001: 구조화된 파일명 생성 로직

작성일: 2026-08-08
대상 프로젝트: Local File AI

## 실험 요약

### 지난 코드의 한계

LLM이 완성된 파일명 문자열과 확장자를 직접 만들기 때문에 파일명 구조가 강제되지
않았고, 이중 확장자와 분류 결과 불일치, Windows 예약 이름 문제가 발생할 수 있었다.

### 변경 코드를 통한 보완점

LLM은 subject, topic, document_type, semester만 추출하고 백엔드가 이를 정규화해
최종 파일명을 조립하도록 변경했다. 분류기의 category를 문서 유형에 반영하고,
원본 확장자와 Windows 파일명 규칙을 백엔드가 결정론적으로 보장한다.

### 그러나 존재하는 한계

첫 페이지 최대 2,000자만 분석하며 subject, topic, semester의 의미 정확성은 여전히
LLM에 의존한다. 같은 이름이 존재할 때 자동 번호 부여와 사용자별 명명 규칙 학습도
아직 지원하지 않는다.


1. 개요
-------

기존 파일명 생성 로직은 로컬 생성형 LLM이 완성된 파일명 문자열을 직접 만들고,
백엔드가 결과의 최소 형식만 검사하는 구조였다.

기존 흐름:

  문서 내용
    → LLM
    → "데이터베이스_정규화_과제_2026-1.pdf"
    → 최소 형식 검증

변경된 흐름:

  문서 내용
    → LLM이 파일명의 의미 요소 추출
    → subject / topic / document_type / semester
    → 백엔드가 정규화, 분류 일치 처리, 확장자 결합
    → "데이터베이스_정규화_과제_2026-1.pdf"

이번 개선의 핵심은 LLM에는 의미 추출을 맡기고, 파일 시스템 형식과 안전성은
결정론적인 백엔드 코드가 담당하도록 역할을 분리한 것이다.


2. 기존 코드의 한계
-------------------

2.1 파일명 구조를 실제로 강제하지 못함

프롬프트는 다음 형식을 요구했다.

  과목명_주제_문서유형_학기.확장자

하지만 백엔드는 파일명이 비어 있지 않은지, 점이 포함됐는지, 일부 금지 문자가
없는지, 150자 이하인지만 검사했다. 따라서 다음처럼 의미 구조가 불완전한 이름도
검증을 통과할 수 있었다.

  과제최종진짜최종.pdf
  정규화.pdf
  2026자료.pdf


2.2 잘못된 확장자가 이중 확장자로 바뀔 수 있음

기존 확장자 보정은 LLM 결과가 원본 확장자로 끝나지 않으면 원본 확장자를 뒤에
추가했다.

  원본 확장자: pdf
  LLM 출력: 보고서.docx
  기존 보정: 보고서.docx.pdf

마지막 확장자는 pdf이므로 적용 계층 검사를 통과할 수 있지만, 사용자에게
부자연스러운 이중 확장자가 제안되는 문제가 있었다.


2.3 분류 결과와 파일명의 문서 유형이 불일치할 수 있음

full 모드에서는 정확도가 더 높은 임베딩 분류기가 LLM의 category를 덮어썼다.
그러나 이미 만들어진 파일명 문자열 내부의 문서 유형은 교정하지 않았다.

예:

  category: assignment
  recommended_filename: 데이터베이스_정규화_강의자료_2026-1.pdf

최종 분류는 과제인데 파일명에는 강의자료가 남을 수 있었다.


2.4 Windows 파일명 제약 검사가 충분하지 않음

기존 코드는 다음 문자만 금지했다.

  \ / : * ? " < > |

그러나 Windows에는 다음 제약도 있다.

  - CON, PRN, AUX, NUL 예약 이름
  - COM1~COM9, LPT1~LPT9 예약 이름
  - 파일명 끝의 점 또는 공백
  - 제어문자

이러한 이름은 추천 단계에서 통과한 후 실제 파일 변경 시 실패할 가능성이 있었다.


2.5 LLM에 너무 많은 책임이 집중됨

기존 LLM은 다음 작업을 모두 담당했다.

  - 파일에서 중요한 정보 판단
  - 과목, 주제, 유형, 학기 결정
  - 구성요소 순서 결정
  - 밑줄 조립
  - 확장자 유지
  - 파일 시스템 금지 문자 회피

생성형 LLM은 의미 추출에는 유용하지만 운영체제 파일명 규칙을 매번 정확하게
준수하는 작업에는 불안정하다.


2.6 완성 문자열의 일부만 교정하기 어려움

다음과 같은 완성된 문자열만 받으면 각 부분의 의미를 백엔드가 확실하게 구분하기
어렵다.

  데이터베이스_정규화_강의자료_2026-1.pdf

따라서 분류기가 assignment라고 판단해도 문자열 안의 강의자료 부분만 안전하게
과제로 교체하기 어려웠다.


3. 변경 코드의 보완점
---------------------

3.1 구조화된 의미 요소 생성

LLM이 완성 파일명 대신 다음 JSON 구조를 생성하도록 프롬프트를 변경했다.

  {
    "subject": "데이터베이스",
    "topic": "정규화",
    "document_type": "과제",
    "semester": "2026-1"
  }

각 필드의 역할이 명확해져 백엔드가 요소별로 검사하고 교정할 수 있게 됐다.


3.2 백엔드의 결정론적 파일명 조립

백엔드의 build_filename() 함수가 다음 순서로 최종 이름을 조립한다.

  subject_topic_document_type_semester.extension

예를 들어 LLM 응답이 다음과 같고:

  subject: 데이터베이스
  topic: 정규화/함수 종속
  document_type: 강의자료
  semester: 2026-1

임베딩 분류 결과가 assignment이면 최종 결과는 다음과 같다.

  데이터베이스_정규화_함수_종속_과제_2026-1.pdf


3.3 분류 결과와 문서 유형 일치

임베딩 분류기의 category를 파일명의 document_type에도 반영한다.

  lecture     → 강의자료
  assignment  → 과제
  report      → 보고서
  reference   → 참고자료
  project     → 프로젝트
  exam_prep   → 시험정리
  career      → 취업문서
  admin       → 행정문서
  personal    → 개인문서
  etc         → 기타

LLM이 강의자료라고 출력했더라도 최종 분류가 assignment이면 파일명에는 과제가
사용된다.


3.4 원본 확장자로 정확히 교체

잘못된 확장자를 뒤에 추가하지 않고 제거한 뒤 원본 확장자로 교체한다.

  기존: 보고서.docx → 보고서.docx.pdf
  변경: 보고서.docx → 보고서.pdf

확장자 결정권은 LLM이 아니라 실제 원본 파일 정보가 가진다.


3.5 파일명 구성요소 정규화

구조화된 각 요소에는 다음 처리가 적용된다.

  - 파일 시스템 금지 문자 제거
  - 제어문자 제거
  - 연속 공백 정리
  - 앞뒤 점, 공백, 밑줄 제거
  - 내부 공백을 밑줄로 변환
  - 값이 없는 구성요소는 최종 이름에서 제외

예:

  입력 topic: 정규화/함수 종속
  정규화 결과: 정규화_함수_종속


3.6 Windows 예약 이름 회피

최종 파일명 stem이 Windows 예약 이름이면 문서_ 접두어를 붙인다.

  CON.pdf → 문서_CON.pdf
  NUL.pdf → 문서_NUL.pdf

Pydantic 계약에도 예약 이름, 제어문자, 파일명 끝 공백 및 끝 점 검사를 추가했다.


3.7 최대 길이 제한

확장자를 포함한 전체 파일명이 FileSuggestion 계약의 150자 제한을 넘지 않도록
확장자 길이를 먼저 확보한 뒤 stem을 제한한다.


3.8 기존 응답 형식과 호환

기존 모델이 다음 형식으로 응답해도 계속 처리할 수 있다.

  {
    "recommended_filename": "데이터베이스_정규화_과제.pdf"
  }

기존 테스트, 이전 프롬프트 응답, 일시적인 구형 모델 출력을 깨뜨리지 않도록
하위 호환성을 유지했다.

구형 응답에 금지 문자가 포함되면 이를 조용히 제거하지 않는다. 기존 동작대로
검증 실패 처리한 후 구체적인 위반 내용을 포함해 LLM에 한 번 재시도한다.


4. 실제 모델 실행 결과
----------------------

사용 모델:

  exaone3.5:2.4b

시험 문서 내용:

  데이터베이스 정규화 과제. 함수 종속성과 제3정규형을 설명하고
  2026년 1학기에 제출한다.

실제 LLM 원시 응답:

  {
    "subject": "데이터베이스",
    "topic": "정규화",
    "document_type": "과제",
    "semester": "2026-1"
  }

백엔드 조립 및 검증 결과:

  {
    "category": "assignment",
    "recommended_folder": "assignment",
    "recommended_filename": "데이터베이스_정규화_과제_2026-1.pdf",
    "confidence": 0.83,
    "reason": "라벨 정의문 유사도 분류 (신뢰도 83%), 파일명은 exaone3.5:2.4b 생성 (slim 모드)"
  }

실행 측정:

  - 모델 응답 시간: 3.11초
  - LLM 재시도: 없음
  - 구조화 JSON 검증: 통과
  - 원본 pdf 확장자 적용: 정상
  - 분류와 파일명의 문서 유형: 일치

7. 남아 있는 한계
-----------------

이번 변경으로 파일명의 구조와 파일 시스템 안전성은 개선됐지만 다음 한계는 남아
있다.

  - 첫 페이지 또는 문서 앞부분 최대 2,000자만 사용하므로 뒤쪽 핵심 정보를
    놓칠 수 있다.

  - subject, topic, semester의 의미적 정확성은 여전히 LLM에 의존한다.

  - 동일한 최종 파일명이 이미 존재하면 자동으로 번호를 붙이지 않고 적용을
    건너뛴다.

  - document_type은 분류기로 교정하지만 subject와 topic의 사실성을 별도로
    검증하지 않는다.

  - 한글과 영문 표기 통일, 사용자별 명명 규칙 학습은 아직 지원하지 않는다.

  - extension_fixed 상태값이 구조화 조립까지 포함하게 되어 이름에 비해 의미가
    넓어졌다.


8. 결론
-------

기존에는 LLM이 최종 파일명을 직접 완성했기 때문에 형식 오류, 이중 확장자,
분류 불일치, Windows 호환성 문제가 발생할 수 있었다.

변경 후에는 LLM이 과목, 주제, 문서 유형, 학기 같은 의미 정보만 추출하고,
백엔드가 이를 안전하게 정규화하여 최종 파일명을 조립한다.

이를 통해 다음 항목이 개선됐다.

  - 파일명 형식의 일관성
  - 원본 확장자의 정확한 보존
  - 임베딩 분류 결과와 파일명의 일치
  - Windows 파일 시스템 호환성
  - LLM 출력에 대한 통제 가능성
  - 기존 응답 및 테스트와의 하위 호환성

실제 exaone3.5:2.4b 모델 실행과 전체 백엔드 테스트를 통해 변경된 로직이 정상적으로
작동하는 것을 확인했다.
