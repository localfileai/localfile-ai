## 2. 전체 결론

실험 전에는 LLM이 완성된 파일명과 확장자를 직접 만들었고, 백엔드는 결과의 최소
형식만 검사했다. 동일 이름이 있으면 적용을 건너뛰었고 PDF는 첫 페이지만 읽었다.

실험 후 현재 구조는 다음과 같다.

```text
문서 최대 5페이지 추출
  → 6,000자 이하 앞·중간·뒤 균형 표본
  → 임베딩 분류 및 RAG 예시
  → slim LLM이 subject/topic/semester만 추출
  → 문서 근거와 대조해 환각 제거
  → 사용자 예시의 한글·영문 표기 관례 반영
  → 백엔드가 문서 유형·확장자를 결합해 파일명 조립
  → Pydantic 안전 검증
  → 사용자 승인
  → 동일 이름이면 안전한 번호 부여
  → 원자적 무덮어쓰기 이동 및 undo 이력 기록
```

주요 정량 결과는 다음과 같다.

```text
실제 생성 모델:                    exaone3.5:2.4b
초기 구조화 생성 측정:              3.11초
5페이지 확장 후 최적화 전 전체:      5.8929초
slim 최적화 후 첫 실행 전체:         2.557초
slim 최적화 후 워밍업 중앙값:        0.390초
최종 전체 백엔드 테스트:             188 passed
```

동일 조건의 보수적인 첫 실행 비교에서는 5.89초에서 2.56초로 약 56.6% 감소했다.
워밍업 후에는 0.37~0.39초에 최종 파일명을 생성했다.

## 4. 최초 코드의 주요 한계

### 4.1 LLM이 최종 파일명을 직접 결정

LLM은 다음을 한 번에 책임졌다.

- 과목과 주제 판단
- 문서 유형과 학기 판단
- 구성요소 순서와 밑줄 조립
- 확장자 유지
- Windows 금지 문자 회피

백엔드는 점과 일부 금지 문자 정도만 검사했으므로
`과제최종진짜최종.pdf`처럼 의미 구조가 불완전한 이름도 통과할 수 있었다.

### 4.2 확장자 보정 오류

원본이 PDF인데 LLM이 `보고서.docx`를 출력하면 기존 로직은 다음처럼 확장자를
뒤에 추가할 수 있었다.

```text
보고서.docx.pdf
```

### 4.3 분류와 파일명 불일치

임베딩 분류기가 category를 `assignment`로 교정해도 LLM이 만든 파일명에는
`강의자료`가 남을 수 있었다.

### 4.4 불완전한 Windows 안전 검증

`CON`, `NUL`, `COM1` 같은 예약 이름, 끝 공백·끝 점, 제어문자를 추천 단계에서
차단하지 않았다.

### 4.5 첫 페이지와 2,000자 입력 제한

PDF는 첫 페이지만 읽었고 추천 입력은 최대 2,000자였다. 제목이나 학기가 뒤쪽에
있으면 LLM이 볼 수 없었다.

### 4.6 동일 파일명 충돌 시 작업 중단

대상 파일이 존재하면 안전을 위해 건너뛰었지만 사용자가 직접 이름을 수정하기
전에는 정리를 완료할 수 없었다.

### 4.7 LLM 의미 출력에 대한 사실 검증 부재

구조화 전환 이후에도 subject, topic, semester가 실제 본문에 있는지 확인하지 않으면
유사 예시의 주제나 모델의 추측이 파일명에 포함될 수 있었다.

### 4.8 불필요하게 긴 slim 생성

slim 모드는 category와 document_type을 이미 알고 있음에도 이를 다시 생성했고,
출력 토큰 상한도 없었다.


## 5. 실험 001: 구조화된 파일명 생성

### 가설

LLM이 완성 문자열을 만드는 대신 의미 요소만 반환하고 백엔드가 파일명을 조립하면
형식과 파일 시스템 안전성을 안정적으로 보장할 수 있다.

### 변경

LLM 출력 계약을 다음처럼 변경했다.

```json
{
  "subject": "데이터베이스",
  "topic": "정규화",
  "document_type": "과제",
  "semester": "2026-1"
}
```

백엔드가 다음 형식으로 조립한다.

```text
subject_topic_document_type_semester.extension
```

함께 적용한 보완:

- 원본 확장자로 정확히 교체
- 분류기의 category로 document_type 교정
- 금지 문자와 제어문자 정리
- Windows 예약 이름 회피
- 끝 공백·끝 점 검사
- 150자 제한
- 기존 `recommended_filename` 형식 하위 호환

### 실제 결과

실제 `exaone3.5:2.4b` 응답:

```json
{
  "subject": "데이터베이스",
  "topic": "정규화",
  "document_type": "과제",
  "semester": "2026-1"
}
```

최종 파일명:

```text
데이터베이스_정규화_과제_2026-1.pdf
```

실제 모델 응답 시간은 3.11초였고 재시도 없이 성공했다. 전체 테스트는 176개가
통과했다.

### 남은 문제

구조는 안전해졌지만 subject/topic/semester의 사실성은 여전히 LLM에 의존했고,
동일 파일명 충돌과 문서 입력 범위 문제도 남았다.


## 6. 실험 002: 동일 파일명 자동 번호 부여

### 가설

기존 파일을 덮어쓰지 않으면서 첫 번째 빈 번호를 선택하면 충돌 때문에 전체 정리
작업이 중단되는 문제를 해소할 수 있다.

### 변경

다음 순서로 후보를 탐색하도록 했다.

```text
데이터베이스_과제.docx
데이터베이스_과제 (1).docx
데이터베이스_과제 (2).docx
```

한 요청 안에서는 `reserved` 집합으로 경로를 예약해 dry-run에서도 두 항목이 같은
경로를 유효하다고 판단하지 않도록 했다. 충돌로 이름이 바뀌면 최종 `target_path`와
`conflict_renamed` 사유를 반환했다.

### 실제 결과

기존 대상:

```text
데이터베이스_과제.docx
데이터베이스_과제 (1).docx
```

새 파일 적용 결과:

```text
데이터베이스_과제 (2).docx
```

기존 파일은 보존됐고 새 파일만 `(2)`로 이동했다. 이력 ID를 이용한 undo도 성공해
원본이 원래 위치로 돌아왔다. 전체 테스트는 178개가 통과했다.

### 남은 문제

`exists()` 확인과 실제 이동이 분리되어 외부 프로세스 경쟁 조건이 남았고, 150자에
가까운 이름에 접미사를 붙이면 길이 제한을 넘을 수 있었다.


## 7. 실험 003: 원자적 충돌 이동과 길이 제한

### 가설

파일 시스템의 원자적인 “대상이 없을 때만 생성” 동작을 사용하면 검사와 이동 사이
경쟁에서 기존 파일을 덮어쓰지 않을 수 있다.

### 변경

`_numbered_target()`이 접미사와 확장자 길이를 먼저 빼고 stem을 줄여 최종 이름이
150자를 넘지 않도록 했다.

실제 이동은 다음 방식으로 변경했다.

```text
os.link(source, target)
  → target이 있으면 FileExistsError
  → 성공하면 source.unlink()
```

hard link 생성은 기존 target을 교체하지 않는다. 다른 작업이 먼저 이름을 확보하면
다음 번호로 재시도한다. 원본 unlink가 실패하면 생성한 링크를 제거해 롤백한다.

### 실제 동시 실행 결과

서로 다른 내용을 가진 두 파일이 동시에 같은 145자 stem을 요청했다.

```text
작업 A → 접미사 없는 149자 이름, 내용 A
작업 B → stem이 축약된 150자 " (1).pdf", 내용 B
```

두 내용이 모두 보존됐고 원본 경로는 제거됐다. 전체 테스트는 180개가 통과했다.

### 실험 중 실패

새 길이 테스트에서 `Path` import를 누락해 최초 실행이 `1 failed, 22 passed`가
됐다. 테스트 코드 import를 수정한 뒤 적용 테스트 23개와 전체 테스트 180개가
통과했다.

### 남은 문제

hard link는 같은 파일 시스템에서만 동작한다. 일부 네트워크 공유, FAT 계열,
다른 볼륨, 특수 마운트에서는 `atomic_move_error`로 실패한다.


## 8. 실험 004: 여섯 잔여 한계 통합 보완

### 8.1 문서 입력 확대

다음 설정과 로직을 추가했다.

```text
MAX_ANALYSIS_CHARS = 6000
MAX_PDF_ANALYSIS_PAGES = 5
```

6,000자를 넘는 긴 문서는 다음 비율로 표본을 만든다.

```text
앞부분 50% + 중간 25% + 뒷부분 25%
```

### 8.2 의미 근거 검증

subject/topic의 일반 문서유형 단어를 제외한 핵심 토큰이 모두 문서에 있을 때만
파일명에 포함한다. semester는 LLM 값 대신 본문의 `2026년 1학기`, `2026-1`
패턴에서 직접 추출한다.

### 8.3 사용자 표기 관례

유사·승인 예시 파일명에서 다음 표기 그룹을 찾아 현재 파일명에 반영한다.

```text
인공지능 ↔ AI
운영체제 ↔ OS
데이터베이스 ↔ DB
컴퓨터네트워크 ↔ 네트워크 ↔ NETWORK
```

### 8.4 상태명 정리

실제 내부 필드를 `extension_fixed`에서 `filename_normalized`로 변경했다.
`extension_fixed`는 구버전 호출자를 위한 읽기 전용 호환 property로 남겼다.

### 실제 5페이지 PDF 실험

1~4페이지에는 일반 정보만 넣고 5페이지에 다음 내용을 넣었다.

```text
인공지능 트랜스포머 과제 2026년 1학기 제출
```

추출기는 5페이지 내용을 정상적으로 읽었다. 그러나 실제 LLM은 유사 예시에서
`머신러닝`을 복사했다.

```json
{
  "subject": "인공지능",
  "topic": "머신러닝 과제",
  "document_type": "과제",
  "semester": "2026-1"
}
```

첫 의미 검증은 `과제`라는 일반어 하나가 본문에 있다는 이유로 `머신러닝 과제`를
통과시켰고 다음 잘못된 이름을 만들었다.

```text
AI_머신러닝_과제_과제_2026-1.pdf
```

이를 근거로 일반어를 제외하고 핵심 토큰 전부가 본문에 있어야 통과하도록 강화했다.
동일한 모델 환각은 최종 파일명에서 제거됐다.

```text
AI_과제_2026-1.pdf
```

모델 생성 시간은 2.94초였고 전체 테스트는 188개가 통과했다.

### 핵심 교훈

사실 검증은 잘못된 정보를 제거할 수 있지만 LLM이 놓친 참 주제 `트랜스포머`를
복구하지는 못했다. 정확성은 높아졌지만 구체성이 낮아질 수 있다.


## 9. 실험 005: slim 생성 속도 최적화

### 병목 측정

5페이지 PDF의 최적화 전 측정:

```text
PDF 추출:          0.1655초
LLM 생성:          5.7257초
검증·조립:         0.0017초
전체:              5.8929초
```

LLM 생성이 전체의 약 97%를 차지했다.

### 첫 최적화 실패

시스템 프롬프트를 지나치게 줄인 첫 시도는 중앙값 3.112초로 빨라졌지만 모델이
세 번 모두 다음처럼 응답했다.

```json
{"filename": "최종"}
```

검증과 재시도 후에도 최종 실패했으므로 성공률 0%인 이 프롬프트는 폐기했다.

### 최종 변경

- slim 출력에서 document_type 제거
- 현재 경로와 상세 폴더 규칙 제거
- slim 전용 최소 사용자 프롬프트 사용
- 허용되는 subject/topic/semester 키 명시
- filename, document_type, 확장자 출력 금지 명시
- Ollama `num_predict=64` 적용

### 최종 반복 측정

| 실행 | 추출 | LLM | 전체 | 결과 |
|---:|---:|---:|---:|---|
| 1 | 0.083초 | 2.473초 | 2.557초 | 성공, 재시도 없음 |
| 2 | 0.003초 | 0.386초 | 0.390초 | 성공, 재시도 없음 |
| 3 | 0.005초 | 0.365초 | 0.370초 | 성공, 재시도 없음 |

중앙값은 0.390초였다. 세 번 모두 다음 최종 파일명을 만들었다.

```text
인공지능_트랜스포머_과제_2026-1.pdf
```

첫 실행 기준으로 5.89초에서 2.56초로 약 56.6% 감소했다. 전체 테스트 188개가
통과했다.


## 10. 여섯 가지 한계의 현재 상태

| 한계 | 현재 상태 | 적용된 보완 | 남은 제약 |
|---|---|---|---|
| 첫 페이지·2,000자 제한 | 부분 해결 | PDF 최대 5페이지, 6,000자 앞·중간·뒤 표본 | 6페이지 이후와 표본 사이 정보 누락 가능 |
| subject/topic/semester의 LLM 의존 | 부분 해결 | 본문 토큰 대조, 본문 학기 직접 추출 | 동의어 이해와 누락 정보 복구는 제한적 |
| 동일 파일명 충돌 시 건너뜀 | 해결 | 번호 자동 부여, 150자 제한, 원자 이동 | hard link 미지원 환경에서는 실패 |
| subject/topic 사실성 미검증 | 부분 해결 | 일반어 제외 후 핵심 토큰 전부 대조 | 문자열 포함 기반이라 의미적 동치에 약함 |
| 표기 통일·사용자 명명 규칙 미지원 | 부분 해결 | 예시 기반 AI·OS·DB·NETWORK 표기 적용 | 사전 네 그룹뿐이며 일반적인 관례 학습 아님 |
| extension_fixed 의미 불일치 | 대부분 해결 | 실제 필드를 filename_normalized로 변경 | 하위 호환 property는 아직 존재 |

따라서 여섯 항목을 모두 코드에서 다뤘지만 완전히 해결된 것은 동일 이름 충돌이며,
나머지는 위험을 줄인 부분 해결 또는 호환성 단계의 해결이다.


## 11. 현재 최종 처리 흐름

### 11.1 추출

- 지원 형식: PDF, DOCX, DOC, PPTX, PPT, HWPX, HWP
- PDF: 앞쪽 최대 5페이지
- 추천 분석 상한: 6,000자
- 긴 문서: 앞·중간·뒤 균형 표본

### 11.2 분류와 RAG

- 문서 임베딩을 한 번 생성해 분류와 RAG에서 공유
- 사용자 승인 예시가 충분히 가까우면 우선 사용
- 그렇지 않으면 라벨 정의문 zero-shot 분류
- 하한 미만이면 `etc`

### 11.3 slim LLM

입력:

- 현재 파일명과 확장자
- 문서 분석 표본
- 표기 관례 참고용 유사 파일명

출력:

```json
{
  "subject": "",
  "topic": "",
  "semester": ""
}
```

생성 상한은 64토큰이다. document_type은 분류기가 채운다.

### 11.4 사실성과 안전 검증

- subject/topic 핵심 토큰의 본문 존재 여부 확인
- semester를 본문에서 다시 추출
- category와 document_type 일치
- 원본 확장자 강제
- Windows 금지 문자·예약 이름 검사
- 최대 150자
- 실패하면 위반 내용을 명시해 LLM 1회 재시도

### 11.5 실제 적용

- 사용자 승인 필수
- root 외부 경로 차단
- 확장자 변경 차단
- 같은 이름이면 번호 부여
- 접미사 포함 150자 제한
- hard link 기반 무덮어쓰기 이동
- 작업 이력 및 undo 제공

## 13. 실험 과정에서 확인된 실패와 교훈

### 13.1 간이 LLM 프롬프트의 빈 JSON

구조화 실험 전 간이 프롬프트에서는 첫 모델 적재에 28.78초가 걸리고 `{}`를
반환했다. 실제 프로젝트 시스템 프롬프트에서는 3.11초에 정상 JSON을 생성했다.

교훈: 모델 성능은 모델 이름뿐 아니라 정확한 시스템 프롬프트 계약에 크게 좌우된다.

### 13.2 테스트가 기존 환각을 정상값으로 기대

본문에 없는 운영체제·스케줄링·학기를 제거하자 기존 테스트가 실패했다. 새 검증
정책에 맞게 테스트 입력과 기대값의 근거를 일치시켰다.

교훈: 기존 테스트 통과가 항상 올바른 제품 동작을 의미하지 않는다. 잘못된 요구를
고정한 테스트는 정책 변경과 함께 수정해야 한다.

### 13.3 유사 예시에서 주제 복사

실제 모델은 AI 표기 예시의 `머신러닝`을 현재 트랜스포머 문서에 복사했다. 일반어
`과제` 하나 때문에 첫 검증을 통과했다.

교훈: RAG 예시는 명명 관례를 전달하면서 동시에 사실 오염을 일으킬 수 있다.
현재 문서 본문을 사실의 최종 기준으로 둬야 한다.

### 13.4 지나친 프롬프트 축약

속도 최적화 첫 시도는 빨랐지만 성공률이 0%였다.

교훈: 생성 속도와 계약 준수율을 함께 측정해야 하며, 단순히 짧은 프롬프트가 좋은
프롬프트는 아니다.

### 13.5 테스트 코드 자체 오류

실험 003의 `Path` import 누락과 실험 005의 금지 문장 문자열 검사처럼 제품 코드가
아닌 테스트 코드에서도 실패가 발생했다. 모든 실패를 보고서에 남기고 원인을
구분했다.


## 14. 현재 남아 있는 주요 한계

### 14.1 문서 범위

- PDF 6페이지 이후 정보 누락 가능
- 6,000자 표본 사이 정보 누락 가능
- 입력 증가로 임베딩·LLM 비용 증가 가능

### 14.2 의미 정확성

- 문자열 포함 기반이라 동의어·약어·번역 표현에 약함
- 환각 제거 후 참 주제를 복구하지 못할 수 있음
- category가 틀리면 document_type도 일관되게 틀림

### 14.3 개인화

- 표기 그룹이 AI·OS·DB·NETWORK 계열에 제한
- 데이터셋 예시와 사용자 승인 예시를 명명 관례에서 엄격히 구분하지 않음
- 사용자의 임의 약칭이나 구성요소 순서를 일반적으로 학습하지 않음

### 14.4 파일 시스템

- hard link는 같은 파일 시스템에서만 가능
- 일부 네트워크 공유와 특수 파일 시스템에서 실패
- 전체 경로 길이 제한 미적용
- 극단적인 롤백 실패 시 같은 파일의 두 이름이 남을 수 있음

### 14.5 성능

- cold start는 여전히 수십 초가 걸릴 수 있음
- full 7.8B 모드는 이번 속도 최적화 대상이 아님
- 실제 `/organize` 전체 시간에는 임베딩과 ChromaDB 조회가 추가됨
- 64토큰 상한은 긴 값에서 JSON을 자를 가능성이 있음

### 14.6 호환성

- `extension_fixed` 호환 property가 남아 있음
- 이전 `recommended_filename` LLM 응답 형식을 계속 지원하므로 제거 시점 관리 필요


## 15. 다음 실험 우선순위

### 1순위: 실제 `/organize` 전체 계측

현재 속도 실험은 추출·LLM·후처리를 측정했지만 임베딩과 RAG는 제외했다. 다음
구간을 각각 계측해야 한다.

```text
추출 / 임베딩 / 분류 / RAG / LLM / 검증 / 응답 직렬화
```

### 2순위: cold start 완화

앱 준비 단계에서 소형 생성 모델을 짧게 워밍업하고, 준비 시간과 첫 사용자 요청
지연의 합을 비교해야 한다.

### 3순위: topic 복구

topic이 사실 검증에서 제거되면 문서의 제목·반복 핵심어·임베딩 유사 구절에서
후보를 추출하는 보수적 복구 경로가 필요하다.

### 4순위: 일반화된 사용자 명명 관례

고정 alias 사전이 아니라 승인된 파일명에서 다음을 통계적으로 추출할 수 있다.

- 한글·영문 선호
- 약어 선호
- 구성요소 순서
- 학기 표기 형식
- 구분자와 대소문자 규칙

### 5순위: 파일 시스템 호환 이동

hard link 사용 가능 여부를 사전에 진단하고, 지원하지 않는 환경에 대해 명확한
사용자 선택과 안전한 대체 정책을 설계해야 한다.


## 16. 최종 평가

실험 001~005를 통해 파일명 생성은 “LLM이 완성 문자열을 결정하는 기능”에서
“LLM이 후보 의미를 추출하고 백엔드가 근거·형식·안전성을 통제하는 기능”으로
변경됐다.

가장 큰 개선은 다음 네 가지다.

1. LLM 출력과 실제 파일 변경 사이에 강한 결정론적 경계가 생겼다.
2. 동일 이름과 동시 접근에서도 기존 파일을 덮어쓰지 않는다.
3. 뒤쪽 문서 정보와 LLM 환각을 함께 다룰 수 있게 됐다.
4. slim 생성의 첫 실행 지연이 약 56.6% 감소했다.

그러나 시스템은 아직 LLM의 의미 추출 품질을 완전히 대체하지 않는다. 실제 실험은
환각을 제거해도 참 주제를 놓칠 수 있음을 보여줬다. 현재 코드는 잘못된 구체성을
허용하기보다 안전하지만 덜 구체적인 파일명을 선택한다.

따라서 현재 상태는 파일 시스템 안전성과 형식 안정성 측면에서는 크게 개선됐고,
의미 품질과 환경 호환성 측면에서는 추가 실험이 필요한 단계로 평가한다.
