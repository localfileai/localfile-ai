# 실험 002: 동일 파일명 충돌 시 안전한 번호 부여

작성일: 2026-08-08
대상 프로젝트: Local File AI

## 실험 목적

실험 001에 남은 한계로 기록된 “동일한 최종 파일명이 이미 존재하면 적용을
건너뛴다”를 개선한다. 기존 파일을 덮어쓰지 않으면서 새 파일을 자동으로 구분하고,
dry-run과 실제 이동, 작업 이력 및 undo가 모두 최종 경로를 일관되게 처리하는지
검증한다.

성공 기준은 다음과 같다.

- 요청한 대상이 비어 있으면 원래 추천 이름을 사용한다.
- 같은 이름이 있으면 `이름 (1).확장자`부터 첫 번째 빈 번호를 선택한다.
- 기존 파일은 내용까지 그대로 보존한다.
- 한 요청 안의 여러 항목은 dry-run에서도 같은 경로를 중복 예약하지 않는다.
- 번호가 붙은 실제 이동도 이력에 기록되고 undo할 수 있다.
- 전체 백엔드 회귀 테스트가 통과한다.

## 지난 코드의 한계

기존 `backend/app/fileops/apply.py`는 대상 경로에 파일이 존재하면 다음 결과로
항목을 건너뛰었다.

```text
status: skipped
reason: conflict: 대상에 같은 이름의 파일이 있습니다
```

이 방식은 덮어쓰기를 막는다는 점에서는 안전하지만, 서로 다른 문서가 같은 추천
파일명을 받으면 사용자가 직접 이름을 수정하기 전까지 정리를 완료할 수 없었다.

또한 dry-run은 실제 파일을 만들지 않으므로 같은 요청 안의 두 항목이 동일한 대상
이름을 요구해도 둘 다 같은 경로를 유효하다고 판단할 가능성이 있었다.

## 변경 코드를 통한 보완점

`backend/app/fileops/apply.py`에 `_available_target()`을 추가했다.

선택 순서는 다음과 같다.

```text
데이터베이스_과제.docx
데이터베이스_과제 (1).docx
데이터베이스_과제 (2).docx
...
```

요청한 경로가 비어 있으면 원래 이름을 그대로 사용한다. 이미 존재하거나 같은
요청에서 예약된 이름이면 1부터 9,999까지 순서대로 검사해 첫 번째 빈 경로를
사용한다.

충돌로 이름이 변경되면 API 결과에 다음 정보를 남긴다.

```text
status: moved 또는 valid
reason: conflict_renamed: 같은 이름이 있어 번호를 붙였습니다
target_path: 실제 선택된 번호 포함 경로
```

추가된 `reserved` 집합은 아직 파일을 생성하지 않는 dry-run에서도 한 요청 안의
대상 경로를 예약한다. 따라서 첫 항목이 `문서.pdf`를 선택하면 다음 항목은
`문서 (1).pdf`를 선택한다.

또한 `_apply_lock`으로 한 서버 프로세스 안에서 여러 apply 요청이 동시에 이름을
검사하고 같은 경로를 선택하는 것을 직렬화했다.

## 변경 파일

### backend/app/fileops/apply.py

- `_available_target()` 충돌 회피 함수 추가
- 번호 탐색 상한 `MAX_CONFLICT_SUFFIX = 9999` 추가
- 요청 단위 경로 예약 집합 추가
- 프로세스 내부 apply 잠금 추가
- 실제 선택된 target_path와 `conflict_renamed` 사유 반환
- 번호가 붙은 최종 경로를 기존 이력 및 undo 흐름에 연결

### backend/tests/test_apply.py

- 기존 충돌 시 skip 테스트를 번호 부여 이동 테스트로 변경
- `(1)`이 존재할 때 `(2)`를 선택하는 테스트 추가
- dry-run 내부 경로 예약 테스트 추가

## 실험 환경과 방법

- 운영체제: Windows
- Python: 프로젝트 `backend/.venv` 런타임
- 대상 형식: DOCX
- 실행 방식: 실제 임시 폴더 및 실제 파일을 생성해 `apply_changes()` 호출
- 기존 대상:
  - `데이터베이스_과제.docx`
  - `데이터베이스_과제 (1).docx`
- 새 원본: `최종.docx`
- 요청 대상 이름: `데이터베이스_과제.docx`

실험에서는 적용 결과를 확인한 뒤 같은 history_id로 undo를 실행했다. 그 후 전체
백엔드 테스트를 실행했다.

## 실제 결과

### 적용 원시 출력

```json
{
  "total": 1,
  "moved": 1,
  "failed": 0,
  "dry_run": false,
  "items": [
    {
      "source_path": "...\\정리대상\\최종.docx",
      "target_path": "...\\정리대상\\과제\\데이터베이스_과제 (2).docx",
      "status": "moved",
      "reason": "conflict_renamed: 같은 이름이 있어 번호를 붙였습니다"
    }
  ],
  "history_id": "20260808-223202-520352"
}
```

### 적용 후 대상 폴더

```text
데이터베이스_과제.docx
데이터베이스_과제 (1).docx
데이터베이스_과제 (2).docx
```

기존 두 파일은 유지됐고 새 파일만 `(2)` 이름으로 이동했다.

### undo 결과

```json
{
  "id": "20260808-223202-520352",
  "restored": 1,
  "skipped": []
}
```

undo 후 원본 `최종.docx`가 원래 위치에 복원된 것도 확인했다.

### 테스트 결과

적용 계층 집중 테스트:

```text
21 passed
```

전체 백엔드 회귀 테스트:

```text
178 passed, 2 warnings
```

실험 001 당시 176개에서 충돌 관련 테스트가 순증해 178개가 됐다. 두 경고는
Starlette TestClient 및 Pillow의 향후 API 변경에 관한 deprecation warning이며
테스트 실패는 아니다.

## 그러나 존재하는 한계

이번 변경 후에도 다음 한계가 남는다.

1. `_apply_lock`은 현재 서버 프로세스 안의 요청만 직렬화한다. 외부 프로그램이나
   다른 서버 프로세스가 경로 확인 직후 같은 파일을 만들면 검사와 이동 사이에
   경쟁 조건이 발생할 수 있다.

2. 이미 150자에 가까운 파일명에 ` (1)` 접미사를 붙이면 운영체제의 파일명 또는
   전체 경로 길이 제한을 넘을 수 있다. 현재 충돌 처리 단계에서는 stem을 다시
   줄이지 않는다.

3. 충돌 시 항상 번호를 붙인다. 사용자가 덮어쓰기, 건너뛰기, 수동 이름 변경 중
   하나를 선택하는 정책 옵션은 아직 없다.

4. 1부터 순차 탐색하므로 동일 stem의 충돌 파일이 매우 많으면 파일 시스템 조회가
   반복된다. 최대 9,999개 이후에는 `conflict_exhausted`로 실패한다.

5. 대소문자를 구분하는 파일 시스템과 구분하지 않는 Windows 파일 시스템 사이의
   이름 동등성 차이를 별도 정책으로 추상화하지 않았다. 현재 실행 중인 파일
   시스템의 `Path.exists()` 결과를 따른다.

6. 실험 001에서 남은 문서 분석 한계인 2,000자 입력 제한, subject/topic/semester의
   의미 정확성, 사용자별 명명 규칙 학습은 이번 실험 범위가 아니므로 그대로 남아
   있다.

## 결론과 다음 실험

동일 파일명이 존재할 때 적용을 중단하던 한계는 안전한 번호 접미사 방식으로
개선됐다. 실제 파일 실험에서 원본 이름과 `(1)`이 있는 상태에서 `(2)`를 선택했고,
기존 파일 보존, 이력 기록, undo 복원을 확인했다. 전체 백엔드 테스트 178개도 모두
통과했다.

다음 실험의 우선 후보는 충돌 접미사를 붙일 때 파일명 길이를 다시 제한하고,
외부 프로세스와의 경쟁에서도 덮어쓰기를 방지하는 원자적 대상 예약 방식이다.
