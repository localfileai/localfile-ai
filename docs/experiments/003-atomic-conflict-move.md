# 실험 003: 길이 제한을 지키는 원자적 충돌 이동

작성일: 2026-08-08
대상 프로젝트: Local File AI

## 실험 목적

실험 002에서 다음 우선 과제로 남긴 두 문제를 개선한다.

1. 150자에 가까운 파일명에 ` (1)` 접미사를 붙이면 길이 제한을 넘을 수 있다.
2. 경로가 비어 있는지 확인한 직후 외부 프로세스가 같은 이름을 만들면 덮어쓰기
   경쟁 조건이 발생할 수 있다.

성공 기준은 다음과 같다.

- 번호 접미사와 확장자를 포함한 최종 파일명이 150자 이하여야 한다.
- 두 작업자가 동시에 같은 이름을 선택해도 기존 결과를 덮어쓰지 않아야 한다.
- 경쟁에서 늦은 작업은 다음 번호 후보로 재시도해야 한다.
- 이동 후 원본 경로가 제거되고 각 파일 내용이 보존돼야 한다.
- 전체 백엔드 테스트가 통과해야 한다.

## 지난 코드의 한계

실험 002의 `_available_target()`은 `Path.exists()`로 후보를 확인한 후 나중에
`shutil.move()`를 실행했다. 확인과 이동이 별도 동작이므로 그 사이에 다른
프로세스가 같은 파일을 생성할 수 있었다.

```text
프로세스 A: target.exists() → false
프로세스 B: 같은 target 생성
프로세스 A: shutil.move(source, target)
```

운영체제와 `shutil.move()` 내부 동작에 따라 마지막 단계에서 오류가 발생하거나
기존 대상이 교체될 가능성을 코드 자체가 명확하게 차단하지 못했다.

또한 번호 후보는 단순히 다음처럼 만들었다.

```python
f"{target.stem} ({number}){target.suffix}"
```

원래 이름이 이미 150자라면 `(1)`을 붙인 결과가 계약의 길이 제한을 초과했다.

## 변경 코드를 통한 보완점

### 접미사를 포함한 길이 계산

`_numbered_target()`이 최종 이름에 들어갈 세 부분의 길이를 먼저 계산한다.

```text
사용 가능한 stem 길이
  = 150 - 확장자 길이 - " (번호)" 길이
```

stem을 사용 가능한 길이로 자르고 끝의 점과 공백을 제거한 뒤 접미사와 확장자를
붙인다. 따라서 `(1)`뿐 아니라 자릿수가 늘어나는 `(10)`, `(100)`도 전체 150자
이하를 유지한다.

### 덮어쓰기 없는 원자적 이동

`_atomic_move_no_replace()`는 `os.link(source, target)`으로 대상 이름을 만든다.
파일 시스템의 hard link 생성은 다음 특성을 가진다.

- target이 없을 때만 성공한다.
- target이 이미 있으면 `FileExistsError`가 발생한다.
- 기존 target을 교체하지 않는다.
- 이름 확보가 파일 시스템 연산 하나로 수행된다.

링크 생성에 성공한 후 원본 이름을 `unlink()`하면 동일 파일 시스템 안에서 내용
복사 없이 move가 완성된다. 원본 제거가 실패하면 새 링크를 삭제해 이동 전 상태로
되돌리도록 했다.

다른 프로세스가 후보를 먼저 차지해 `FileExistsError`가 발생하면 다음 번호 후보를
선택해 다시 시도한다.

```text
원래 이름 실패 → 이름 (1) → 이름 (2) → ...
```

## 변경 파일

### backend/app/fileops/apply.py

- `MAX_FILENAME_CHARS = 150` 추가
- `_numbered_target()` 길이 안전 후보 생성 함수 추가
- `_atomic_move_no_replace()` 원자적 무덮어쓰기 이동 추가
- 실제 적용 경로를 `exists() + shutil.move()`에서 `os.link() + unlink()`로 변경
- 경쟁 중 `FileExistsError`가 발생하면 다음 번호로 재시도
- 지원되지 않는 파일 시스템 오류를 `atomic_move_error`로 구분

### backend/tests/test_apply.py

- 150자 이름 충돌 후에도 최종 길이가 150자 이하인지 검증
- 첫 후보를 외부 프로세스가 선점한 상황을 주입해 `(1)` 재시도 검증
- 권한 오류 테스트를 새로운 원자적 이동 경계에 맞게 변경

## 실험 환경과 방법

- 운영체제: Windows
- 파일 시스템: 현재 임시 작업 폴더가 위치한 Windows 파일 시스템
- Python: 프로젝트 `backend/.venv` 런타임
- 파일 형식: PDF
- 동시 실행 도구: `ThreadPoolExecutor(max_workers=2)`
- 입력 파일: 서로 다른 내용을 가진 `source-a.pdf`, `source-b.pdf`
- 요청 대상 stem: 한글 `가` 145자

두 작업자가 동시에 같은 대상 이름에 `_atomic_move_no_replace()`를 실행하도록 했다.
`FileExistsError`를 받은 작업자는 `_numbered_target()`으로 다음 후보를 만들어
재시도했다.

이 실험은 애플리케이션의 `_apply_lock` 바깥에서 직접 원자적 이동 함수를 동시에
호출했다. 따라서 단순히 프로세스 내부 잠금이 직렬화한 결과가 아니라 파일 시스템
연산 자체의 충돌 동작을 검증했다.

## 실제 결과

### 동시 실행 출력

```json
[
  {
    "source": "source-a.pdf",
    "target": "가...(145자 stem)...가.pdf",
    "length": 149,
    "content": "A"
  },
  {
    "source": "source-b.pdf",
    "target": "가...(축약된 stem)...가 (1).pdf",
    "length": 150,
    "content": "B"
  }
]
```

확인 결과:

- 첫 작업은 접미사 없는 149자 이름을 확보했다.
- 경쟁한 두 번째 작업은 stem이 축약된 정확히 150자 `(1).pdf` 이름을 확보했다.
- 대상 파일 내용은 각각 `A`, `B`로 유지됐다.
- 두 원본 경로는 모두 제거됐다.
- 기존 대상 덮어쓰기는 발생하지 않았다.

### 테스트 과정에서 발생한 실패

첫 적용 계층 테스트 실행은 다음 결과였다.

```text
1 failed, 22 passed
NameError: name 'Path' is not defined
```

새 길이 테스트에서 `pathlib.Path` import를 빠뜨린 테스트 코드 오류였다. import를
추가한 뒤 같은 테스트를 다시 실행했다. 제품 코드의 원자적 이동 실패는 아니지만,
실험 지침에 따라 최초 실패도 기록한다.

### 최종 테스트 결과

적용 계층 집중 테스트:

```text
23 passed, 1 warning
```

전체 백엔드 회귀 테스트:

```text
180 passed, 2 warnings
```

두 경고는 Starlette TestClient와 Pillow의 deprecation warning이며 테스트 실패는
아니다. `git diff --check`도 통과했다.

## 그러나 존재하는 한계

1. hard link는 원본과 대상이 같은 파일 시스템에 있어야 한다. 선택한 root 내부에
   다른 볼륨으로 연결되는 junction이나 특수 마운트가 있으면 `EXDEV` 등의 오류가
   발생하고 현재는 `atomic_move_error`로 해당 항목을 실패 처리한다.

2. FAT 계열, 일부 네트워크 공유, 권한이 제한된 파일 시스템처럼 hard link를
   지원하지 않는 환경에서는 새 이동 방식이 동작하지 않는다. 안전하지 않은
   덮어쓰기 방식으로 자동 폴백하지 않는 대신 실패를 명시하도록 선택했다.

3. hard link 생성 후 원본 unlink가 실패하면 새 링크를 제거해 롤백하지만, 롤백
   삭제까지 실패하는 극단적인 권한·장치 오류에서는 같은 파일을 가리키는 두 이름이
   남을 수 있다. 내용 손실은 아니지만 이동이 완전히 원복되지는 않는다.

4. 150자는 Python 문자열 코드 포인트 기준이다. 이모지처럼 UTF-16에서 두 코드
   단위를 사용하는 문자가 많으면 Windows API 관점의 길이와 다를 수 있다.

5. 파일명 한 구간은 150자로 제한하지만 전체 경로 길이는 별도로 계산하지 않는다.
   깊은 대상 폴더에서는 Windows 전체 경로 제한이나 애플리케이션별 제한을 만날 수
   있다.

6. 충돌 정책은 여전히 자동 번호 부여 한 가지다. 사용자가 건너뛰기, 수동 변경,
   명시적 교체 중 하나를 선택하는 API 옵션은 없다.

7. 실험 001부터 남은 문서 입력 2,000자 제한, 의미 정확성, 사용자별 명명 규칙
   학습은 이번 파일 적용 실험 범위가 아니므로 남아 있다.

## 결론과 다음 실험

실험 002에서 확인한 접미사 길이 초과와 검사-이동 경쟁 조건을 보완했다. 실제 동시
파일 시스템 실험에서 두 작업이 원본 이름과 `(1)` 이름을 각각 얻었고, 최대 길이는
150자로 유지됐으며 두 파일 내용도 보존됐다. 전체 백엔드 테스트 180개가 통과했다.

다음 실험의 우선 후보는 hard link를 사용할 수 없는 파일 시스템을 사전에 감지해
사용자에게 정확한 복구 방법을 안내하는 기능, 또는 전체 경로 길이를 고려해 폴더와
파일명 길이를 함께 제한하는 기능이다.
