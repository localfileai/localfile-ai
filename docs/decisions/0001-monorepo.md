# ADR-0001. 단일 저장소로 간다

- **상태**: 승인
- **날짜**: 2026-07-27
- **결정자**: 팀 전원

## 맥락

팀이 BE1·BE2·FE1·FE2 네 파트로 나뉘어 있습니다. 담당이 명확히 갈라져 있으므로
저장소도 사람 수만큼 나누는 안이 자연스러워 보였습니다.

하지만 기획안의 4주차 결과물은 **설치 파일 하나**입니다.

```
server.exe (BE1 + BE2, PyInstaller)
    └─ 포함 ─→ LocalFileAI_Setup.exe (FE1 + FE2, Electron Builder)
```

즉 네 파트의 산출물이 마지막에 하나로 합쳐집니다.

## 검토한 선택지

### A. 파트별 저장소 4개 (`be1` `be2` `fe1` `fe2`)

담당과 저장소가 1:1로 맞아 소유권이 명확합니다. 각자 자기 저장소에서
독립적으로 커밋할 수 있습니다.

문제는 통합입니다.

- FE2가 만든 React 컴포넌트를 앱에서 띄워보려면 매번 FE1 저장소로 옮겨야 합니다.
  같은 `package.json`, 같은 빌드에 속하는 코드가 저장소로 갈라집니다.
- BE1의 `rag/`와 BE2의 `api/`는 같은 FastAPI 앱에 import됩니다.
  저장소가 다르면 서로를 패키지로 배포하거나 서브모듈을 걸어야 합니다.
- 3주차 "폴더 선택 → 분석 → 추천 → 승인 → 실제 이동" 전체 사이클을 붙일 때
  네 저장소의 커밋을 수동으로 맞춰야 합니다. 어느 조합이 동작하는 상태인지
  기록되지 않습니다.
- 계약(Pydantic 스키마)이 바뀌면 네 저장소에 각각 PR을 열어야 합니다.
  하나만 늦게 병합되면 그 사이 `main`은 깨진 상태입니다.

### B. 앱별 저장소 2개 (`fe` `be`)

빌드 산출물 단위와 맞습니다. A의 문제 대부분이 사라집니다.

다만 계약 변경 시 두 저장소에 PR을 열어야 하는 문제는 남습니다.
프론트엔드 타입은 백엔드 Pydantic 모델에서 생성되므로, 생성물과 원본이
다른 저장소에 있으면 CI가 최신 여부를 검사할 수 없습니다.

### C. 단일 저장소 (선택)

```
localfile-ai/
├── apps/desktop/    FE1 + FE2
├── apps/server/     BE1 + BE2
└── packages/contracts/
```

## 결정

**C를 선택합니다.**

근거:

1. **통합이 커밋 단위로 검증됩니다.** 어느 시점의 `main`을 체크아웃해도
   그 조합은 함께 CI를 통과한 상태입니다. 4주차 패키징 때 "어느 버전끼리 맞나"를
   찾을 필요가 없습니다.
2. **계약 변경이 원자적입니다.** Pydantic 모델과 생성된 TypeScript 타입이
   한 PR에 함께 들어갑니다. CI가 생성물 최신 여부를 검사할 수 있습니다.
3. **소유권은 저장소가 아니라 디렉터리로 나눕니다.**
   [CODEOWNERS](../../.github/CODEOWNERS)가 경로별 리뷰어를 자동 지정합니다.
   A안의 장점인 명확한 소유권은 그대로 유지됩니다.
4. **경로 필터로 CI를 분리합니다.** 프론트엔드만 고친 PR에서 파이썬 CI가
   돌지 않습니다. 저장소를 나눠서 얻으려던 격리는 이걸로 충분합니다.

## 결과

**좋아지는 것**

- 전체 사이클을 붙일 때 저장소 간 버전 맞추기가 사라집니다
- 이슈·PR·마일스톤이 한곳에 모여 진행 상황을 한 화면에서 봅니다
- 계약 변경이 한 PR로 끝납니다

**나빠지는 것 / 감수하는 것**

- 클론 용량이 커집니다. 4주 프로젝트 규모에서는 무시할 수준입니다.
- 개인 기여도가 저장소 단위로 드러나지 않습니다.
  → CODEOWNERS의 디렉터리 소유권과 커밋 scope(`feat(rag):`, `feat(ui):`)로
    누가 무엇을 했는지 추적 가능합니다.
- 한 사람의 `main` 푸시 실수가 전원에게 영향을 줍니다.
  → `main` 브랜치 보호와 PR 필수로 막습니다.

## 부수 결정

- BE1의 기존 1주차 작업물(`localfile-ai-be1/`)은 `apps/server/experiments/`로
  옮깁니다. 실험 코드와 프로덕션 코드를 같은 디렉터리에 두지 않습니다.
- `develop` 브랜치는 만들지 않습니다. 4주 일정에서 릴리스 브랜치 관리 비용이
  얻는 것보다 큽니다. 주차별 태그(`v0.1.0` ~ `v1.0.0`)로 대신합니다.
