# ADR-0002. 로컬 LLM은 `exaone3.5:7.8b`, 임베딩은 `bge-m3`

- **상태**: 승인
- **날짜**: 2026-07-27
- **결정자**: 강인혁 (BE1 · AI/DB)
- **계획서 항목**: BE1 ① ChromaDB 세팅·임베딩 환경 / BE1 ③ 학습용 베이스 모델 선정

> **수치 출처**: BE1의 1주차 실측입니다. 1주차 병합 검증에서는 **재현하지 않았습니다**
> (Ollama 모델 내려받기 시간). 재현 명령은 맨 아래에 있습니다.

## 1. 로컬 LLM — `exaone3.5:7.8b`

### 맥락

기획안은 `EEVE-Korean-10.8B` 또는 `Llama-3-8B-Instruct`를 **예시로** 들었습니다.
실측으로 정해야 했습니다.

| 제약 | 내용 |
|---|---|
| VRAM | 8GB (RTX 3060 Ti) → 7~8B 라인 |
| 한국어 | 대상 문서가 한국어입니다 |
| JSON 출력 | `app/contracts/ai.py`의 `FileSuggestion`을 통과해야 합니다 |
| 응답 시간 | 파일 수십 개를 순차 처리하므로 건당 시간이 누적됩니다 |

**`EEVE-Korean-10.8B` 제외**: Q4 기준 약 6.5GB로 VRAM 8GB에서 여유가 없습니다.
일반 사양 PC에서 돌지 않으면 제품이 성립하지 않습니다.

### 측정 조건

동일 표본 **40건** · `seed 42` · `temperature 0.1` · `format: json` · **순차 실행**
프롬프트는 첫 페이지 텍스트만 제공 (RAG 미적용 = 1주차 베이스라인)

> 실험은 하나씩 돌립니다. 동시에 돌리면 GPU 경합으로 응답 시간이 왜곡됩니다.

### 1차 측정 — 모델 응답을 그대로 검증

| 모델 | ② 분류 | ③ 파일명 | 토큰F1 | JSON 유효 | 평균 응답 |
|---|---|---|---|---|---|
| llama3.1:8b | **100.0%** | 75.0% | 69.1% | 100.0% | 4.25s |
| qwen2.5:7b | 95.0% | 75.5% | 48.4% | 100.0% | 4.38s |
| exaone3.5:7.8b | 57.5% | 85.6% | 66.2% | **62.5%** | 4.35s |

exaone이 40건 중 15건 탈락했고, 원인은 **전부 확장자 누락 하나**였습니다.

```
'인공지능_자연어처리_문장임베딩_2026-1'            <- .pdf 없음
'운영체제_프로세스_스케줄링_과제_2026-1'           <- .txt 없음
'데이터베이스_SQL_최적화_인덱스_설계_과제_2025-2'   <- .md 없음
```

파일명 내용은 오히려 정확합니다. 확장자는 원본 파일에서 백엔드가 이미 아는 값이라
후처리 한 줄로 붙일 수 있습니다. 이 상태로 순위를 매기면 왜곡되므로 재측정했습니다.

### 2차 측정 — 확장자 자동 보정 후 (최종 근거)

`test_models.py --autofix-extension` · 세 모델 모두 동일 적용

| 모델 | ② 분류 | ③ 파일명 | 토큰F1 | 한국어 유지 | JSON | 응답 |
|---|---|---|---|---|---|---|
| **exaone3.5:7.8b** | 95.0% | **88.5%** | 63.4% | **100.0%** | 100% | **4.19s** |
| qwen2.5:7b | 95.0% | 75.0% | 48.3% | 85.0% | 100% | 4.28s |
| llama3.1:8b | **100.0%** | 73.5% | **69.2%** | 97.5% | 100% | 4.29s |

### 파일명 구성요소별 포함률

정답 규칙이 `과목_주제_문서유형_학기.확장자`라서 요소별로 쪼개 봤습니다.

| 요소 | exaone3.5 | qwen2.5 | llama3.1 |
|---|---|---|---|
| 과목 | 85.0% | 60.0% | 75.0% |
| 주제 | **100.0%** | 82.5% | 95.0% |
| 문서 유형 | 60.0% | 70.0% | **95.0%** |
| 학기 | **97.5%** | 62.5% | **2.5%** |
| 확장자 | 100% | 100% | 100% |

**`llama3.1`의 학기 2.5%가 결정적입니다.** 40건 중 39건에서 학기를 빠뜨립니다.
파일명에 학기가 없으면 나중에 자료를 찾을 때 쓸모가 크게 떨어집니다.

### 한국어 유지율

한국 대학생용 앱이므로 파일명이 영어로 바뀌면 사용자가 자기 파일을 못 알아봅니다.

| 모델 | 한국어 유지 | 영어로 번역된 사례 |
|---|---|---|
| **exaone3.5:7.8b** | **100.0%** | 0건 |
| llama3.1:8b | 97.5% | 1건 |
| qwen2.5:7b | 85.0% | **6건** |

```
qwen2.5 사례:
  database_normalization_summary_2026-1.md
    정답 데이터베이스_관계형_데이터베이스_정규화_논문_요약_2026-1.md
  ai_2025_2_cnn_image_classification.md
    정답 인공지능_합성곱_신경망_기반_이미지_분류_강의자료_2025-2.md
```

### 결정

**`exaone3.5:7.8b` 채택.** 차선 `llama3.1:8b`. `qwen2.5:7b` 제외.

| 근거 | 수치 |
|---|---|
| ③ 파일명 품질이 15%p 앞섬 | 88.5% vs llama3.1 73.5% |
| 학기 포함률이 결정적으로 앞섬 | 97.5% vs llama3.1 2.5% |
| 한국어 100% 유지 (유일하게 영어 번역 0건) | 100.0% |
| 응답이 가장 빠름 | 4.19s |
| ② 분류는 5%p 뒤짐 | 95.0% vs llama3.1 100.0% |

분류에서 5%p 뒤지지만 파일명에서 15%p 앞서고 학기·한국어에서 압도적입니다.
기능②(분류)와 기능③(파일명)이 모두 MVP 핵심이므로 종합 점수가 높은 쪽을 골랐습니다.

**`qwen2.5:7b` 제외 이유**: 한국어 유지율 85%가 이 제품에는 맞지 않습니다.

### ⚠️ 필수 후속 조치

**`recommended_filename`에 확장자가 없으면 원본 확장자를 붙이는 후처리.**
이게 없으면 exaone의 JSON 유효율이 **62.5%로 떨어집니다** (1차 측정 참고).

계획서 3주차 "Pydantic 에러 검증 및 재시도 로직"에 이 처리를 포함하면 됩니다.
2주차에 Mock을 실제 Ollama로 교체하는 시점에는 이미 들어가 있어야 합니다.

## 2. 임베딩 모델 — `bge-m3`

기획안 기술 스택에 `AI: Ollama, 다국어 임베딩 모델, 소형 로컬 LLM`이라고 명시돼 있습니다.
ChromaDB를 그냥 쓰면 기본값으로 **영어 전용** 모델(`all-MiniLM-L6-v2`)이 붙는데,
한국어 문서에서는 사실상 동작하지 않습니다.

| | ChromaDB 기본값 (영어 전용) | **`bge-m3` (다국어)** |
|---|---|---|
| 차원 | 384 | 1024 |
| "데이터베이스 정규화" 검색 | 무관한 파일 반환 | **정답 1위** |
| 거리 분포 | 0.85 ~ 1.18 (변별 불가) | 0.25 ~ 0.35 (명확) |

거리가 좁은 구간에 뭉치면 관련도 순위 자체가 의미를 잃습니다.

### 임베딩 실행 결과

| 항목 | 값 |
|---|---|
| 벡터 DB | ChromaDB 1.5.9 · `PersistentClient(path="./chroma_db")` |
| 컬렉션 | `file_documents` |
| 거리 방식 | 코사인 |
| 모델 | `bge-m3` (Ollama 로컬, 다국어, 1024차원, 1.2GB) |
| 색인 건수 | 1,000건 전수 |
| 소요 시간 | 120초 (8.3건/s) |

### 자연어 검색 품질 (기능①)

사용자가 실제로 칠 만한 **구어체 질의 23건**으로 측정했습니다.
문서 제목을 그대로 베끼지 않고 "공개키 암호화 정리한 거" 같은 표현을 썼습니다.

| 지표 | 결과 |
|---|---|
| Recall@5 | 100.0% |
| P@5 | 100.0% |
| Top-1 정확도 | 100.0% (23/23) |
| MRR | 1.000 |
| 응답 시간 | 평균 2,777ms · 중위 2,290ms |

```
"OSPF BGP 비교한 문서"     → 1위: 라우팅 프로토콜 비교   (거리 0.3149)
"공개키 암호화 정리한 거"    → 1위: 대칭키와 공개키 암호   (거리 0.3218)
"퀵소트 시간복잡도 정리"     → 1위: 정렬 알고리즘 성능 분석 (거리 0.3315)
```

**BE1이 직접 남긴 단서 두 가지** — 이 100%를 그대로 믿으면 안 됩니다.

1. **평가셋이 쉬운 편입니다.** 주제 20종이 서로 잘 구분되고 질의 키워드가 본문에
   등장합니다. 실제 사용자 파일은 주제가 겹치고 표현이 흐릿해 더 어렵습니다.
2. **질의당 2.3초는 검색창 UX로 느립니다.** 대부분 질의 임베딩 시간입니다.
   계획서 3주차 "모델 최적화" 항목으로 넘겨야 합니다.

## 3. 결정이 코드 어디에 반영돼 있는가

| 결정 | 반영 위치 |
|---|---|
| 임베딩 `bge-m3` | `backend/scripts/embed_dataset.py` → `DEFAULT_MODEL = "bge-m3"` |
| 임베딩 `bge-m3` (실험용) | `backend/scripts/test_models.py` → `--embed-model` 기본값 |
| 컬렉션 · 코사인 | `embed_dataset.py` → `COLLECTION_NAME` · `metadata={"hnsw:space": "cosine"}` |
| LLM `exaone3.5:7.8b` | `test_models.py` → `DEFAULT_MODELS` **첫 번째 항목** |

> ⚠️ **1주차에는 LLM을 런타임에서 쓰지 않습니다.** AI 추천이 전부 `/mock/*`
> 하드코딩이라 모델을 고정할 설정 파일이 아직 없습니다. `DEFAULT_MODELS`는
> 후보 목록이라 "무엇이 선정됐는지"를 코드만 봐서는 알 수 없습니다 —
> **그래서 이 문서가 그 결론의 단일 출처입니다.**
>
> 2주차에 Mock을 실제 Ollama 연동으로 바꿀 때 `OLLAMA_GENERATE_MODEL` /
> `OLLAMA_EMBED_MODEL`을 설정 한 곳(`.env` 또는 `app/core/config.py`)에 모으고,
> 기본값을 **`exaone3.5:7.8b` / `bge-m3`** 로 두어야 합니다.

## 5. GPU 없는 PC 실측 (2026-07-30 추가)

위 수치는 모두 RTX 3060 Ti 기준입니다. **AMD 내장 그래픽 PC(CPU 추론)** 에서
다시 재봤습니다. GPU 유무의 영향이 작업별로 완전히 다릅니다.

| 작업 | RTX 3060 Ti | CPU | 격차 |
|---|---|---|---|
| 문서 임베딩 (색인) | 8.3건/s | 0.22건/s | 38배 |
| 질의 임베딩 (검색) | 2.3초 | 2.8초 | **1.2배** |
| LLM 추천 (기능②③) | 4.19초/파일 | **81.1초/파일** | **19배** |

### 질의 지연은 모델 문제가 아니다

한 요청에 담는 질의 수를 늘려 분해했습니다.

```
1건: 2.806초 · 5건: 3.183초 · 10건: 3.790초
  -> 고정비용 2.696초 + 질의당 계산 0.109초
  -> 지연의 96.1%가 요청당 고정 오버헤드
```

**따라서 "질의당 2.3초" 항목의 원인 지목을 수정합니다.** 임베딩 계산은 0.11초이고
나머지는 요청 오버헤드입니다. GPU를 붙이거나 모델을 줄여도 해결되지 않습니다.
커넥션 재사용(`requests.Session`), `keep_alive`, 배치 처리가 실효 대책입니다.

또 하나: **Ollama는 요청을 직렬 처리합니다.** 색인 중에 질의를 보내면 47.4초까지
대기했습니다. 2주차 증분 인덱싱을 붙일 때 검색이 멈추지 않도록 큐를 분리해야 합니다.

### ⚠️ 기능②③이 GPU 없는 PC에서 실용 범위를 벗어난다

`exaone3.5:7.8b` CPU 실측 3건: 116.4초 / 75.7초 / 81.1초 (계약 통과 3/3).
**추천 품질은 정상이고 속도만 문제입니다.** 파일 30개 폴더에 약 40분입니다.

원인은 인코더 대 디코더 구조입니다. 임베딩은 입력 전체를 한 번의 순전파로 처리하지만,
LLM은 출력 토큰마다 가중치 4.44GB 전체를 메모리에서 다시 읽습니다 —
연산량이 아니라 **메모리 대역폭** 문제입니다(CPU 약 50GB/s vs 3060 Ti 약 448GB/s).

기획안 타깃이 "Windows를 사용하는 20대 대학생"이므로 외장 GPU가 없는 사용자가 많습니다.
**2주차에 Mock을 실제 LLM으로 교체하기 전에 대책을 정해야 합니다.**

| 대책 | 비고 |
|---|---|
| 더 작은 모델 병행 (3~4B) | 한국어 파일명 품질을 이 문서 기준으로 재측정 |
| 백그라운드 처리 + 진행률 | 계획서 4주차 "로딩 바"를 2주차로 앞당김 |
| 선택한 파일만 추천 | 폴더 전체 대신 |
| GPU 없으면 경고 후 축소 모드 | 기대치 관리 |

## 5-1. 저사양 PC 대책 — 실측으로 81초 → 13초 (2026-07-30)

기획안 타깃이 "Windows를 사용하는 20대 대학생"이므로 **외장 GPU가 없는 PC에서
돌아가야 합니다.** GPU 없이 81초/파일은 쓸 수 없습니다. 두 가지를 실측했습니다.

### ① 분류(기능②)를 LLM에서 떼어낸다 — k-NN

이미 계산해 둔 임베딩으로 최근접 이웃의 카테고리를 다수결하면 됩니다.
검색용 임베딩을 재사용하므로 **추가 비용이 0**입니다.

처음 측정한 100%는 **데이터셋 인공물**이었습니다. 생성기가 (주제 20 × 유형 6) =
120조합으로 1,000건을 만들어 조합당 8건씩 본문이 거의 같습니다.
top-1 이웃이 **100% 같은 주제·같은 유형의 쌍둥이**였고 거리가 0.0176이었습니다.

그래서 **같은 주제를 전부 배제**해(= 처음 보는 주제) 다시 재측정했습니다.

| 방식 | 정확도 | 파일당 비용 |
|---|---|---|
| 무작위 (6종) | 16.7% | — |
| 최빈 클래스 | 약 18.1% | — |
| **k-NN k=3 (같은 주제 배제)** | **96.0%** | **0초** |
| k-NN k=1 / k=5 | 94.5% / 95.0% | 0초 |
| exaone3.5:7.8b (GPU) | 95.0% | 4.19초 |
| exaone3.5:7.8b (CPU) | 95.0% | 81.1초 |

top-1 거리 중위 0.2744로 §2의 실제 검색 분포(0.25~0.35)와 맞아 현실적입니다.
**LLM과 동등하거나 낫고 공짜입니다.**

> 그래도 "분류를 LLM 경로에서 제거할 수 있다"는 구조적 결론은 유효합니다.

### ② 출력 토큰을 줄이고 모델을 줄인다

디코더는 출력 토큰마다 가중치 전체를 다시 읽으므로 **생성 시간이 출력 길이에 비례**합니다.
분류를 k-NN이 맡으면 LLM은 파일명 한 줄만 만들면 됩니다.

동일 표본 3건 · CPU · 중위값입니다.

| 모델 | 출력 계약 | 평균 출력 토큰 | 중위 시간 |
|---|---|---|---|
| `exaone3.5:7.8b` | full (5필드) | 143 | 47.8초 |
| `exaone3.5:7.8b` | **slim (파일명만)** | 31 | **29.7초** |
| `exaone3.5:2.4b` | full (5필드) | 172 | 23.9초 |
| **`exaone3.5:2.4b`** | **slim (파일명만)** | **31** | **13.0초** |

두 조치를 합치면 **81.1초 → 13.0초 (6.2배)** 입니다.

`exaone3.5:2.4b`(1.53GB)는 같은 계열이라 한국어 출력이 유지됩니다. 위 표본에서도
`알고리즘_동적계획법_그리디_강의자료_2026-1.pdf` 처럼 한국어 파일명이 나왔습니다.

> ⚠️ **품질은 별도로 측정해야 합니다.** 위는 속도 측정이고 표본 3건입니다.
> 2.4b의 파일명 점수·학기 포함률·한국어 유지율을 `test_models.py --sample 40 --seed 42`로
> 7.8b와 같은 기준으로 재야 채택 여부를 정할 수 있습니다. slim 계약에서
> 학기가 빠진 사례(`..._과제_2025.txt`)가 관찰됐습니다.

### ③ 권고 — 사양별 동작 계층

| 사양 | ① 검색 | ② 분류 | ③ 파일명 추천 |
|---|---|---|---|
| **GPU 없음 (내장 그래픽)** | `bge-m3` 2.8초 | **k-NN 0초** | `exaone3.5:2.4b` slim **13초** |
| **GPU 8GB 이상** | 동일 | k-NN 0초 (또는 LLM) | `exaone3.5:7.8b` full 4.19초 |

저사양에서 파일 30개 폴더는 **약 6.5분**입니다(기존 40.5분). 여기에 백그라운드 처리와
진행률 표시를 붙이면 감당할 수 있는 수준입니다.

**함께 필요한 조치**

- `reason` 필드 유지 여부 결정 (미해결 논의 #4). slim 계약에서 제거하면 시간이 절반입니다
- Ollama는 요청을 직렬 처리합니다(§5). 색인과 추천이 겹치면 서로 막습니다 — 큐 분리 필요
- GPU 유무를 감지해 계층을 자동 선택하고, 사용자에게 예상 시간을 먼저 알려 줄 것

→ **BE1 · AI 결정 필요.** 2주차에 Mock을 실제 LLM으로 교체하기 전에 정해야 합니다.

## 6. 재검토 시점

- **2주차 RAG 주입 실험 후.** 유사 예시를 넣었을 때 분류·파일명이 얼마나 오르는지에
  따라 모델보다 검색 개선에 자원을 더 쓸지 판단합니다.
  `test_models.py --with-rag` 옵션이 이미 있습니다.
- **검색 평가셋을 어렵게 만든 뒤.** 현재 100%는 쉬운 평가셋 결과이므로
  임베딩 모델 판단의 전제가 바뀔 수 있습니다.
- **GPU 없는 PC 대책 결정 시.** §5의 81초/파일을 어디까지 줄일지에 따라
  모델 선정 자체를 다시 볼 수 있습니다. → **BE1 · AI 결정 필요**
