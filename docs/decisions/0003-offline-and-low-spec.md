# ADR-0003. 오프라인 동작과 저사양 PC 지원

- **상태**: 제안 (2주차 시작 전 결정 필요)
- **날짜**: 2026-07-30
- **제기**: 강인혁 (BE1)
- **관련**: [ADR-0002 §5 · §5-1](0002-model-selection.md)

기획안의 두 전제를 다시 확인하는 문서입니다.

> "문서를 외부 서버로 보내지 않고 내 PC 안에서 찾고 정리합니다"
> "핵심 타겟: Windows를 사용하는 20대 대학생"

---

## 1. 오프라인 — 추론은 이미 로컬입니다

### 측정

Ollama 프로세스의 외부 TCP 연결을 추론 전후로 확인했습니다.

```
추론 전 외부 연결 : 0건
추론 실행         : 응답 정상 (17.3초)
추론 후 외부 연결 : 0건
```

**모델 파일이 PC에 있으면 인터넷 없이 동작합니다.** 기획안의 "외부 서버로 보내지 않는다"는
약속은 지켜집니다.

### 진짜 문제는 provisioning입니다

인터넷이 필요한 시점은 **모델을 처음 받을 때 한 번**입니다.
계획서 4주차 목표가 "개발 툴이 전혀 없는 PC에서 `setup.exe` 하나로 설치"인데
여기에 걸립니다.

| 넣어야 할 것 | 크기 |
|---|---|
| Ollama 런타임 | 약 600MB |
| `exaone3.5:7.8b` | 4.44GB |
| `exaone3.5:2.4b` (저사양용) | 1.53GB |
| `bge-m3` | 1.08GB |

`setup.exe`에 전부 넣으면 6GB를 넘습니다.

### 선택지

| 안 | 설치 파일 | 첫 실행 | 비고 |
|---|---|---|---|
| **A. 최초 실행 시 다운로드** | 수십 MB | **인터넷 필요** | "오프라인 앱" 약속과 어긋남 |
| **B. 모델 포함 배포** | 6GB+ | 오프라인 가능 | USB·외장하드 배포용 |
| **C. 둘 다 제공** | 둘 다 | 상황별 | 빌드 파이프라인 2개 |

**C를 권합니다.** 기본은 A로 가볍게 배포하고, **"오프라인 설치판"을 따로 하나** 만듭니다.
발표·시연 환경에 인터넷이 없을 수 있으므로 B가 반드시 하나는 있어야 합니다.

저사양 계층만 담으면 `exaone3.5:2.4b` + `bge-m3` = **2.6GB**로 줄어듭니다.
오프라인 설치판은 이 조합으로 만드는 편이 현실적입니다.

### Ollama 의존을 줄이는 선택지 (4주차 판단)

Ollama는 내부적으로 **llama.cpp**를 씁니다. `llama-cpp-python`을 직접 쓰면
별도 런타임 설치 없이 `server.exe` 안에 추론 엔진을 넣고 `.gguf` 모델 파일만
옆에 두면 됩니다.

- **장점**: Ollama 설치 단계가 사라짐. 배포 구조가 단순해짐
- **단점**: BE2의 PyInstaller 빌드가 복잡해짐 (네이티브 확장 번들링)

→ **2주차는 Ollama로 가고, 4주차 패키징 시점에 판단합니다.** 지금 바꾸면
2주차 일정이 흔들립니다.

## 2. 저사양 PC — 81초를 13초로 줄였습니다

### GPU가 필요한 것은 앱 전체가 아니라 LLM 하나입니다

작업별로 병목이 다릅니다 (측정 근거는 [ADR-0002 §5](0002-model-selection.md)).

| 작업 | 병목 | CPU에서 |
|---|---|---|
| 임베딩 검색 | 요청 오버헤드 (계산 0.11초) | **2.8초 — 문제 없음** |
| LLM 추천 | 메모리 대역폭 | **81초/파일 — 못 씀** |

인코더(임베딩)는 입력을 한 번의 순전파로 처리합니다. 디코더(LLM)는 출력 토큰마다
가중치 전체를 다시 읽습니다. 그래서 GPU 유무가 LLM에만 크게 작용합니다.

### 대책 두 개를 합쳐 6.2배

[ADR-0002 §5-1](0002-model-selection.md)의 측정 결과입니다.

1. **분류를 k-NN으로** — 임베딩 재사용, 추가 비용 0, 정확도 96.0% (LLM 95.0%)
2. **출력 축소 + 소형 모델** — `exaone3.5:2.4b` slim 계약

```
exaone3.5:7.8b full :  81.1초/파일   (기존)
exaone3.5:7.8b slim :  29.7초/파일
exaone3.5:2.4b full :  23.9초/파일
exaone3.5:2.4b slim :  13.0초/파일   <- 6.2배 개선
```

### 결정 사항 — 사양별 동작 계층

| 사양 | ① 검색 | ② 분류 | ③ 파일명 추천 | 30개 폴더 |
|---|---|---|---|---|
| **GPU 없음** | `bge-m3` 2.8초 | k-NN 0초 | `exaone3.5:2.4b` slim 13초 | **약 6.5분** |
| **GPU 8GB+** | 동일 | k-NN 0초 | `exaone3.5:7.8b` full 4.19초 | 약 2분 |

기존 40.5분에서 6.5분으로 줄어듭니다. 여기에 백그라운드 처리와 진행률을 붙이면
저사양에서도 쓸 수 있습니다.

### 함께 해야 할 것

| 항목 | 담당 | 비고 |
|---|---|---|
| `exaone3.5:2.4b` 품질 측정 | BE1 | `test_models.py --sample 40 --seed 42`로 7.8b와 동일 기준. slim에서 학기 누락 관찰됨 |
| `reason` 필드 유지 여부 | BE1 · FE2 | 미해결 논의 #4. 제거하면 생성 시간 절반 |
| 색인·추천 큐 분리 | BE2 | Ollama는 요청을 직렬 처리. 색인 중 검색이 47초까지 대기함 |
| GPU 감지 후 계층 자동 선택 | BE2 | 사용자에게 예상 시간을 먼저 표시 |
| 진행률 · 백그라운드 처리 | FE1 · FE2 | 계획서 4주차 "로딩 바"를 2주차로 앞당김 |

## 3. 아직 확인하지 못한 것

- **실제 사용자 파일에서의 k-NN 정확도.** 합성 데이터셋은 본문에 `문서 유형:`이
  글자로 적혀 있습니다. 실제 파일에는 없습니다
- **`exaone3.5:2.4b`의 파일명 품질.** 속도만 재고 품질은 3건 관찰뿐입니다
- **다른 저사양 환경.** 이번 측정은 AMD 내장 그래픽 · RAM 15.3GB 한 대 기준입니다.
  RAM 8GB PC에서는 7.8B 모델이 스왑을 타 더 나빠질 수 있습니다
