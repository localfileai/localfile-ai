## 알게 된 것

### 1. 데이터셋 라벨이 입력과 무관하면 모델 비교가 무의미하다

초기 데이터셋은 category를 **무작위로** 붙이고 있었습니다.
문서 내용과 라벨 사이에 아무 관계가 없었습니다.

```
                          수정 전        수정 후
정보 이득 (문서 유형)      0.0364 bit     2.3817 bit
정보 이득 (두 신호 모두)   --             2.9857 bit  = H(category) 전량

정확도 상한
  무작위                   12.5%          12.5%
  최빈 클래스              --             15.3%
  문서 유형만 읽음         17.0%          72.8%
  문서 유형 + 수행 형태     --            100.0%
```

수정 전에는 **본문을 완벽히 읽어도 17.0%가 상한**이었습니다.
이 데이터로 "qwen2.5가 낫다"는 결론을 냈었고, 그건 무효였습니다.

지금은 16개 (문서 유형 × 수행 형태) 조합이 전부 단일 category로 결정적 매핑됩니다.
`analyze_label_signal.py`가 이걸 자동 검증하고 실패 시 exit 1을 냅니다.

**교훈**: 모델을 비교하기 전에 데이터셋에 신호가 있는지부터 검증한다.

### 2. 프롬프트에 관례를 주면 20.0% → 70.0%

같은 모델, 같은 표본입니다. 모델을 키우는 것보다 "이 사용자가 평소 어떻게
정리하는지"를 알려주는 쪽이 압도적으로 큽니다.

**이 50%p가 2주차 RAG의 목표 구간입니다.** 유사 예시 주입만으로 얼마나
회수하는지가 이 프로젝트의 핵심 지표가 됩니다.

### 3. 한국어 검색이 사실상 동작하지 않는다

100건 임베딩 후 한국어 쿼리 3건. 스크립트는 3/3 부합으로 출력했지만
**그 수치를 믿으면 안 됩니다.**

| 쿼리 | 1위 결과 | distance | 판정 |
|---|---|---|---|
| 데이터베이스 정규화 과제 | `..._실험_결과.txt` | 0.85 | 주제 무관 |
| 머신러닝 실험 결과 | `클라우드_환경의_분산_처리_구조_조사_자료.docx` | 0.89 | 주제 무관 |
| 팀 프로젝트 회의록 | `..._프로젝트.csv` — 숫자 행뿐인 CSV | 1.18 | 무의미 |

원인 두 가지:

1. **기본 임베딩 모델이 영어 중심** (`all-MiniLM-L6-v2`). distance가 0.85~1.18
   전 구간에 뭉쳐 변별이 되지 않습니다.
2. **CSV가 인덱스를 오염시킨다.** 임베딩 100건 중 14건이 CSV이고, 본문은
   `sample_id,feature_1,...` 뒤 난수 행입니다. 의미 임베딩할 내용이 없는데도
   상위 결과로 올라옵니다.

그리고 평가 기준 자체가 헐거웠습니다. "1위 결과의 category가 납득 가능한가"는
라벨 규칙 수정 후 오히려 더 통과하기 쉬워졌습니다. 검색 품질은 개선되지 않았는데도요.
